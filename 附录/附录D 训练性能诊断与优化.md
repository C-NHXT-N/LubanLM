# 附录 D：训练性能诊断与优化

50M 模型已经在 RTX 4060 Ti 上训练，显存还有余量，GPU 利用率却只有约 36%。如果只看这个百分数，很容易想到“把批次调大”或“把所有 CPU 核心都用上”。但训练慢可能发生在不同地方：CPU 还没有提交下一项运算，GPU 正在等待数据，或者程序为了打印一个数字，正在等待前面的计算全部完成。先分清等待发生在哪里，才知道应该改哪段代码。

本附录记录 2026 年 10 月 2 日的一次实际优化。我们保持同一个模型、同一批数据和每次更新的样本数，将预训练短测速度从约 5,569 提升到 27,231 Token/s，约为原来的 4.89 倍。下面从电脑占用开始，逐步解释这个变化。完整测量表保存在 [Win11 训练效率优化实测](../docs/Win11训练效率优化.md)，这里侧重解释原因和判断方法。

## 先看电脑在等待什么

这次使用 Win11、Python 3.10.21、PyTorch 2.6.0+cu124，训练卡是 RTX 4060 Ti 16GB；电脑有 6 个物理核心、12 个逻辑处理器，系统可用总内存约 15.93 GiB。模型实际参数量为 49,558,400，训练序列长度为 256。另一张 GTX 1650 没有承担本次训练。

性能迁移完成后，在预训练继续运行时取了 5 次系统采样。下表是这一时段的观察记录，并非整轮训练的峰值；它与短测表使用不同的采样窗口。

|观察项|这 5 次采样中的占用|怎样理解|
|---|---:|---|
|全系统 CPU|17%～19%|按所有逻辑处理器的总能力计|
|训练进程 CPU|约 97%～102%|按一个逻辑处理器计，100% 约相当于全机的 1/12|
|系统内存|已用约 12.33～12.34 GiB，可用约 3.59～3.60 GiB|包括训练、控制器、浏览器、系统等所有程序|
|训练进程驻留内存|约 2.26 GiB|进程当前驻留在 RAM 中的页面|
|控制器驻留内存|约 1.03 GiB|CPU 内存占用，与 GPU 显存是两种资源|
|RTX 4060 Ti|利用率 68%～75%，显存约 3,576 MiB|显存约 3.49 GiB；利用率描述采样期间的忙碌时间|
|RTX 4060 Ti 功耗、温度|约 104 W、56～58°C|同时记录，用于比较不同设置下的运行状态|
|GTX 1650|利用率 0%，显存 0 MiB|本时段未观察到计算负载|
|全机磁盘读、写速率|约 0.287、0.307 MiB/s|这是全机磁盘统计，不能直接当作 D 盘单独的速率|
|D 盘剩余空间|约 114.31 GiB|影响能否继续保留数据、检查点与日志|

这里的 GiB 是字节数除以 `2**30`，MiB 是字节数除以 `2**20`。显卡商品名中的“16GB”与软件显示的单位也要区分。多个进程的驻留内存可能包含共享页面，因此不能把这些数字简单相加，当成系统已用内存。

全机 CPU 只有 18%，并不说明训练进程还有五倍提速空间。训练进程消耗了约一个逻辑处理器的时间，可能是 Python 在顺序发起许多操作；这条执行链不能自动平分给 12 个逻辑处理器。线程也可能在核心之间迁移，这个百分数不能证明某一个固定核心一直被占满。

同样，GPU 利用率 75% 不等于使用了理论算力的 75%。`nvidia-smi` 的 GPU 利用率表示采样期间至少有一个计算核函数正在执行的时间比例，并不直接测量每秒完成了多少浮点运算。一个很小的运算也能让 GPU 被计为“正在工作”。所以我们的主要比较指标是单位时间内处理的有效 Token 数，利用率帮助解释这个结果。[NVIDIA 对利用率的定义](https://docs.nvidia.com/deploy/nvidia-smi/index.html#utilization)

在 PowerShell 中，下面两条只读命令可以查看两张卡和系统内存，不会启动训练。第二条输出的是总内存和空闲物理内存，空闲值与其他工具的“可用内存”口径可能不同。

```powershell
nvidia-smi --query-gpu=name,utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu --format=csv

Get-CimInstance Win32_OperatingSystem | Select-Object `
    @{Name='TotalGiB';Expression={$_.TotalVisibleMemorySize / 1MB}}, `
    @{Name='FreeGiB';Expression={$_.FreePhysicalMemory / 1MB}}
```

`Win32_OperatingSystem` 的这两个原始字段按 KiB 计；PowerShell 中 `1MB` 的数值为 `2**20`，所以上面的结果按 GiB 表示。运行时还应查看实际训练进程、日志和当前阶段：验证、保存检查点或等待人工评分时，GPU 占用自然会与训练时不同。

原设置的短测中，CPU 准备批次大约占测量时间的 0.1%。语料已经提前转成 Token，并通过内存映射读取；训练过程中不需要每一步重新分词。因此，增加数据加载进程并不是本次最先验证的方向。我们先检查每次送入 GPU 的工作量，以及训练循环里的同步和调度开销。

## 同样 8 条序列，为什么一次送入更快

假设一次参数更新需要使用编号 1～8 的八条序列，每条长 256 个输入位置。原设置先计算 `[1, 2]`，再计算 `[3, 4]`，之后是 `[5, 6]` 和 `[7, 8]`。每组都执行前向计算和反向传播，但四组结束后才调用一次优化器更新参数。

一次实际送入模型的序列数叫微批次（micro batch）；更新前重复前向、反向的次数叫梯度累积次数（gradient accumulation）。两者相乘，是这次更新使用的有效批次。

|设置|前向、反向的分组|每次更新的序列数|每次更新的输入位置数|
|---|---|---:|---:|
|微批次 2，累积 4|`[1,2] [3,4] [5,6] [7,8]`|8|2 × 4 × 256 = 2,048|
|微批次 4，累积 2|`[1,2,3,4] [5,6,7,8]`|8|4 × 2 × 256 = 2,048|
|微批次 8，累积 1|`[1,2,3,4,5,6,7,8]`|8|8 × 1 × 256 = 2,048|

三个设置都使用八条序列，优化器都更新一次，区别在于 GPU 同时计算的内容。小模型一次只处理两条序列时，矩阵较小，CPU 需要反复提交四组运算。一次处理八条序列，矩阵运算能同时安排更多工作，也减少了分组之间的调度开销。代价是同时保留更多中间张量，显存通常会上升。

下面的 Python 小例子只演示分组，不使用 PyTorch 或 GPU。运行后可以看到三种分组都覆盖编号 1～8，且每次更新对应 2,048 个输入位置。

```python
samples = list(range(1, 9))
length = 256
for micro_batch in (2, 4, 8):
    groups = [samples[i:i + micro_batch]
              for i in range(0, len(samples), micro_batch)]
    accumulation = len(groups)
    print(micro_batch, accumulation, groups, len(samples) * length)
```

梯度累积还要保证损失的权重正确。预训练中各组长度相同，可以把每组平均损失按组数分摊。SFT 中，提示词和 padding 的标签会被设为 `-100`，不参与答案损失；不同组的监督位置数可能不同。例如两组分别有 3 个和 1 个监督位置，正确权重是 `3/4` 与 `1/4`。如果各乘 `1/2`，就会改变这次更新的训练目标。实现见 [训练执行路径](../training/execution.py) 中的 `update()`。

分组相同的八条样本，在数学上可以得到同一个平均梯度；实际 BF16 运算改变相加顺序后会有浮点误差。因此本次迁移检查了样本顺序、损失和梯度，没有把“有效批次相同”当成逐位一致的保证。

显存剩余很多，也不代表应直接把微批次从 8 改为 16。当前累积次数已是 1，改成 16 会让有效批次翻倍，每次更新的样本数、更新总步数与学习率安排都需要重新考虑。这已经超出了本次保持训练条件的执行优化。

## 减少程序中不必要的等待

Python 发起一个 GPU 运算后，通常可以继续提交后面的运算，无须等它立即完成。可以把 CPU 理解为提交任务的一方，GPU 按队列执行。若 Python 此时要拿到 GPU 上某个数的确切值，CPU 就必须等到相关计算完成。这个等待叫 CPU 与 GPU 同步。

原训练循环在每个微批次上把损失转成 Python 数字，统计 GPU 上的监督位置数，并在每步末尾显式等待 GPU。下面摘出其中两类操作；`loss` 和 `y` 都已位于 GPU，这些语句依赖训练上下文，不是独立运行脚本。

```python
loss_number = float(loss.detach())
targets = int((y != -100).sum())
```

`detach()` 只是让这个损失张量不再跟随梯度计算，并没有把它移回 CPU；随后调用 `float()` 才需要取出数值。`int()` 读取 GPU 上的计数时也一样。一次只取一个数，数据量很小，但等待可能打断 CPU 连续提交任务。[PyTorch 性能调优指南](https://docs.pytorch.org/tutorials/recipes/recipes/tuning_guide) 将这类读取标量、转换为 CPU 数据的操作列为应留意的同步点。

优化后，标签还在 CPU 时就统计监督位置数；用于日志的损失保留为已经脱离梯度图的 GPU 张量，到日志输出点再转成 Python 数字。对应的局部代码如下，`losses` 是当前更新的统计量，不会无限保存历史计算图。

```python
# loss_for() 中：y 此时还在 CPU。
targets = int((y != -100).sum())

# update() 中：loss 还在 GPU，仅累积日志统计量。
losses += loss.detach() * targets
```

这个修改保留了更新前的非有限损失检查和梯度检查。如果产生 `NaN` 或无穷值，要在优化器更新前拦住。当前 `bool(torch.isfinite(losses))` 和带 `error_if_nonfinite=True` 的梯度裁剪仍然可能同步；为了保证检查点不会被异常更新污染，本次保留这些检查。提速来自减少重复等待，而不是删除全部检查。

另一个开销在 GPU 时间账本。原路径每步都把累计时间写入 JSON；优化路径每步仍检查时间是否到达预算，但约每 5 秒才持久化一次，正常退出或达到上限时强制写入。这样减少了热循环里的文件操作。实现见 [GPU 时间账本](../scripts/common.py) 的 `GPUBudget.tick()`。异常终止可能留下最后一段尚未写入的时间，恢复时仍需核对真实进程和日志，补齐结算；不能通过删账本获得额外预算。

这些循环修改一起构成 `optimized` 路径。仅保持微批次 2、累积 4 时，速度从约 5,569 提升到 5,764 Token/s，增幅约 3.5%。这说明循环优化有效，但在这次实验里，把同时计算的微批次增大带来了更明显的变化。

## 把零散运算交给合适的执行后端

微批次改成 8 后，我们继续比较优化器、注意力和数据传输的实现。它们保持同一个训练目标，但让 CPU 发起运算、GPU 读取中间数据的方式发生变化。

AdamW 更新每个参数时，需要结合梯度、历史一阶与二阶统计量以及权重衰减。若许多参数张量分别执行这些小运算，CPU 会提交很多工作。融合 AdamW（fused AdamW）把更新过程中的多项操作合并执行，减少单独调度和中间读写。本次在已加载旧 Adam 状态之后，显式设置 `foreach=False`、`fused=True`，并将其步数张量放到对应设备；仅在构造优化器时设置选项，会被后来加载的状态覆盖。实际代码在 [执行配置](../training/execution.py) 的 `configure_optimizer()` 中。

模型的手写注意力路径依次计算 `Q @ K.T`、缩放、掩码、Softmax，再乘 `V`。这条路径便于学习和验证。性能路径调用 PyTorch 的缩放点积注意力接口（SDPA），由它选择适合当前设备、精度和张量形状的实现。下面是 [注意力模块](../model/blocks.py) 中的局部调用；Q、K、V 以及因果、padding 掩码都在前面的代码中准备好。

```python
attention_output = F.scaled_dot_product_attention(
    query, key, value,
    attn_mask=allowed,
    is_causal=causal,
    dropout_p=0.0,
)
```

SDPA 是一个接口，不能仅凭调用名字就宣称使用了 FlashAttention。本次 profiler 实际记录到了 `aten::_scaled_dot_product_efficient_attention` 及其前向、反向操作，因此记录为高效注意力后端（efficient attention）。具体后端受输入条件约束，计算的分组方式也可能带来数值差异。[PyTorch 2.6 SDPA 文档](https://docs.pytorch.org/docs/2.6/generated/torch.nn.functional.scaled_dot_product_attention.html)

掩码检查不能省略。训练时每个位置只能看自己和之前的位置；SFT 的 padding 不能被当成有效内容；带 KV cache 的生成中，当前 Query 与全部 Key 形成长方形，而不是普通的同长方阵。我们保留手写路径作为验证参考，分别检查这些情况。

最后是从 CPU RAM 向 GPU 显存传输批次。普通 CPU 内存可能被操作系统换页，锁页内存（pinned memory）则能为传输提供固定的页面。`BatchTransfer` 为每个累积槽和输入列保留可复用的锁页缓冲区，再用 `non_blocking=True` 发起设备传输，减少反复分配和传输过程中的主机等待。[PyTorch 2.6 锁页缓冲区说明](https://docs.pytorch.org/docs/2.6/notes/cuda.html#use-pinned-memory-buffers)

```python
# BatchTransfer.prepare() 中：首次遇到该形状时建立 CPU 缓冲区。
buffer = torch.empty(value.shape, dtype=value.dtype, pin_memory=True)
buffer.copy_(value)

# loss_for() 中：从准备好的 CPU 批次传入 GPU。
x = x.to(device, non_blocking=True)
```

这是局部示意，完整实现会复用缓冲区，并在 SFT 形状变化时替换当前槽的缓冲区，避免缓存所有历史形状。本次更新前的同步检查确保上一次传输完成后才重用这些缓冲区。锁页内存占用的是 RAM，不能无限增加。

`non_blocking=True` 表示允许主机不在这个调用点等待传输完成；它本身不能保证传输与 GPU 计算完全重叠。当前默认流中的工作仍按顺序执行，若要跨批次预取和并行传输，还需要独立的流、依赖管理和缓冲区生命周期设计。因此，这次只按整条传输路径的实测结果记录收益。

BF16 混合精度、提前将语料转成 Token、内存映射读取以及 `zero_grad(set_to_none=True)` 在原训练中已经存在。它们是本次比较的共同条件，没有作为新增优化再计一次收益。我们也没有靠缩短序列、删掉语料或降低验收标准获得速度提升。

## 用同一个起点比较，才能知道改动是否有效

短测从第 53,810 步、110,202,880 个本轮 Token 的同一个检查点开始。每个候选都恢复模型、优化器和随机状态，使用相同的八条样本序列；先预热 20 步，随后计时 100 步，重复三次，取 Token/s 的中位数。预热用于让初始化和缓存建立的开销不主导比较。

GPU 是异步执行的。如果只测量 Python 提交完任务的时间，GPU 可能还没算完。测量程序在计时区间开始和结束处同步，确保统计的是已经完成的工作。[PyTorch 2.6 异步执行与计时说明](https://docs.pytorch.org/docs/2.6/notes/cuda.html#asynchronous-execution)

|预训练候选|相对上一阶段增加的设置|中位有效输入 Token/s|GPU 平均利用率|采样到的整卡峰值 MiB|
|---|---|---:|---:|---:|
|`baseline-2x4`|原循环，微批次 2、累积 4|5,569|36.1%|2,476|
|`optimized-2x4`|减少循环内重复同步和账本写入|5,764|37.2%|2,476|
|`optimized-4x2`|改成微批次 4、累积 2|10,606|41.8%|2,854|
|`optimized-8x1`|改成微批次 8、累积 1|18,673|65.3%|3,801|
|`fused-adamw`|融合 AdamW|22,848|72.9%|3,802|
|`sdpa`|SDPA 高效注意力路径|25,009|66.9%|3,795|
|`pinned-transfer`|可复用锁页缓冲区与非阻塞传输|27,231|72.9%|3,795|

表中设置按顺序叠加。例如最后一行同时保留微批次 8、优化循环、融合 AdamW 和 SDPA。相邻行可帮助判断在这个组合下是否值得继续采用某项改动，但不能把它们当成各项优化在任意环境中的独立贡献。循环修改本身也包含多处变化，表格没有分离每一处的收益。

注意 SDPA 一行的 GPU 利用率从 72.9% 降到 66.9%，Token/s 却继续提高。这就是不能以“利用率越高越好”代替吞吐比较的实际例子。显存列来自定期采样到的整张卡占用峰值，可能漏掉很短的瞬间；它与 PyTorch 记录的活跃张量峰值、缓存分配器保留峰值也不是同一口径。

SFT 单独进行了同样的三次短测：原设置约 1,784，采用优化循环、微批次 8、累积 1、融合 AdamW、SDPA 和锁页传输后，有效输入速度达到约 8,927 Token/s，约为原来的 5.00 倍。这是整组设置的结果。这里“有效输入”排除 padding，但仍包含提示词；真正参与答案损失的监督 Token 由另一个计数记录。不能用 padding 填充得越多来制造更高的有效吞吐，也不能直接拿 SFT 和预训练的 Token/s 比较训练难度。

这些短测包含训练更新与必要的批次准备，排除了定期验证和检查点保存时间。因此，“4.89 倍”描述的是这次预训练循环短测，不代表整轮训练的总时间必然缩短到原来的 `1/4.89`。正式训练还要计算验证、保存、阶段切换与人工能力审阅的时间。

原始数据保存在 [性能对照 JSON](../docs/run-results/chat-v2/performance_comparison.json)，测量实现见 [短测程序](../scripts/benchmark_training.py)。实际上线后又记录了 GPU 利用率 72%～83%、温度 55～57°C 等状态，见 [上线核验 JSON](../docs/run-results/chat-v2/performance_rollout.json)。不同窗口的采样数值会变化，不能拼成一个并不存在的“同时峰值”。

## 快了以后，还要能正确恢复

本次数值比较要求损失绝对差不超过 0.01，梯度相对 L2 误差不超过 2%。相对 L2 误差是把所有参数梯度的差看成一个长向量，比较它的长度占参考梯度长度的比例。选定的预训练路径损失差约 0.000521，梯度误差约 0.9517%，通过了这一短测门槛。门槛只说明本次执行迁移可以继续验证，不证明所有后续训练结果必然相同。

检查还覆盖样本与采样随机状态一致、因果与 padding 掩码、矩形 KV cache、SFT 监督位置加权、非有限损失拦截。随后进行了真实磁盘恢复检查：用小型验证模型连续更新四步，与更新两步后保存、从文件恢复再更新两步比较，模型权重、优化器、随机数和采样状态在相同设置下完全一致。记录见 [磁盘恢复核验](../docs/run-results/chat-v2/execution_resume_checks.json)，实现见 [恢复检查程序](../scripts/verify_execution.py)。这是恢复机制的检查，与改变分组后逐位一致是两个不同问题。

正式训练保留严格的普通 `--resume`。只有显式 `--migrate-execution` 才允许更改这次批准的执行设置，并要求有效批次保持不变。模型参数、Adam 状态、学习率位置、采样位置和已保存 Token 进度都从检查点恢复。固定验证继续使用手写注意力与微批次 2，避免同时改变验证方法；验证损失比切换前参考值恶化超过 0.1 时，控制器保留异常权重并回退。

所有性能与恢复检查实际消耗约 13.72 分钟 GPU 时间，计入原预算。本轮总上限仍是 1,440 分钟，其中预训练最多 1,200 分钟，SFT 含阶段 probe 最多 180 分钟，其余留给验收。固定 5,000 条阶段 probe 保持原执行设置，用于前后比较；完整 SFT 才使用已通过检查的新执行设置。

这次切换还留下一个值得学习的恢复错误。等待新检查点的代码把文件修改时间 `13:49:20.xxx` 与记录到整秒的 `13:49:20` 直接比较，旧文件也满足“大于该时间”，导致程序没有等到下一次保存就停止了训练。最后只能从 110,202,880 Token 的完整保存点恢复；最近日志已经达到 119,808,000 Token，所以至少 9,605,120 个未保存 Token 需要重跑，约对应此前 28 分钟的更新。

代码已修正时间精度比较，切换源权重也独立保留并核对 SHA256。重跑使用的 GPU 时间仍保留在账本里；原日志中较大的 Token 数不能继续当成当前权重的进度。后续判断切换条件，应确认新检查点完成保存、其步数确实前进，再核对权重、优化器和随机状态。时间戳只能帮助定位，不能独自证明保存成功。

## 还能更快时，先提出可以验证的假设

当前吞吐已达到约 2.7 万 Token/s，但仍有进一步优化的可能。一次更新的 profiler 中出现了数百次 `to`、`copy_`、转置、乘法和矩阵运算调用。这支持继续检查零散操作与 CPU 调度开销的方向；profiler 本身有额外开销，其百分比不能直接作为正式训练的耗时占比。`to` 和 `copy_` 还可能是 GPU 内部的精度转换，不能看到这些名字就认定 PCIe 数据传输是瓶颈。

|后续假设|为什么值得检查|还需要验证什么|
|---|---|---|
|缓存固定形状的 RoPE 位置量和掩码|减少每层、每步重复构造|长度、设备、精度和 KV cache 改变时能正确失效|
|减少重复精度转换，融合 RMSNorm 等小运算|可能减少中间读写与调度次数|损失与梯度误差、训练稳定性、实际后端和吞吐|
|使用编译或 CUDA Graph|可能减少 Python 与驱动反复提交运算的开销|当前 Win11 环境能否支持，图捕获、恢复和异常检查能否兼容|
|改变有效批次或序列长度|可能改变硬件工作量与吞吐|需要作为新的训练实验，重新安排学习率并比较能力，不能沿用本次迁移结论|

CUDA Graph 会记录一组 GPU 工作，之后重复执行，从而减少 CPU 每次重新发起所有运算的开销。但它要求可捕获部分使用固定形状和内存地址，不能在捕获内部读取 GPU 标量到 CPU。当前更新前的 Python 异常检查、SFT 变长批次都需要专门设计；不能只套一层包装就认为问题解决。[PyTorch 2.6 CUDA Graph 说明](https://docs.pytorch.org/docs/2.6/notes/cuda.html#cuda-graphs)

本机环境当时没有安装 Triton。是否采用编译、额外融合内核或迁移到 WSL，需要单独验证依赖、正确性和恢复成本。本轮按已通过测量的设置继续训练，上表保留为待验证方向。0.5B 也需要独立测量微批次、显存和吞吐，不能把 50M 的 4.89 倍收益直接套用过去。

性能比较完成后，下一项工作是回到 [50M 聊天训练闭环](../docs/50M聊天训练闭环.md)：用独立题目检查回答是否可读、相关、正确以及是否循环，再验证导出、重载和真实聊天命令。更高的 Token/s 能让同一预算学到更多内容，是否已经学会简单聊天仍要由这些实际回答决定。

## 2026-10-03：降低padding后，为什么几乎没有加速

在同一个v5检查点和固定抽取的1024条v6语义样本上，我们保留SDPA、fused AdamW、微批次8，预热10步后测量完整128批，重复三次。每个候选都处理这1024条样本；长度分桶只改变组批与次序。结果见[第二次SFT性能对照](../docs/run-results/chat-v2/sft-correction-performance.json)。

|新增候选|中位非填充输入Token/s|padding位置占比|相对原组批|
|---|---:|---:|---:|
|原组批，无预取|6,979|39.65%|1.000|
|连续缓冲区，预取2批|6,697|39.65%|0.960|
|长度分桶，预取2批|6,954|3.87%|0.997|

原组批准备数据约0.067秒，完整测量约9.35秒，仅约0.7%。预取需要队列、线程和独立缓冲区，开销反而抵消这点工作。分桶确实减少了无用位置，但50M短序列中的许多小运算与主机提交开销还在，端到端更新没有明显变快。新选项未达到15%采用门槛，因此预取与分桶没有上线；缓冲区路径可显式用于任务元数据，不声称它自身提速。

三步profiler中出现2442次`to`、1221次`_to_copy`、1761次乘法、1830次转置和702次矩阵乘法。这提示继续检查重复转换与零散操作；profiler有额外开销，不能拿表内CPU与CUDA耗时相加推算正常训练时间，也不能把所有`copy`当成主机向显卡传输。

这次GPU约42%～47%、功耗约62～65W，温度没有到散热限制。CPU进程约占一个逻辑核。机器还有空余资源，但把其他核心或显存填满不是训练目标；先确定哪个改动能提高监督Token/s并保持正确性。本轮没有为占满显卡改变有效批次或移除数值检查。

这里的非填充输入计数沿用attention mask口径，仍含提示；不同组批中短样本末尾EOS可能留在输入列，因此同一语义数据的输入计数有很小差异。三组每轮实际监督Token均为19,575，更适合跨组批比较。后续日志同时给出含padding位置、非填充输入和监督Token/s，避免以填充制造提速。

预取代码虽未上线，恢复检查仍值得保留。生产者可能已提前读两批，检查点必须存消费者已经训练过的游标和随机状态，不能存生产者更靠后的位置。真实磁盘恢复与跨epoch测试均通过，见[修复检查](../docs/run-results/chat-v2/correction_checks.json)。相同设置的精确恢复，不等于分桶改变样本顺序后仍会得到相同权重。

另外，v5开发检查虽达88.3%，首次独立验收只有61.7%。能力问题与速度问题必须分别验证。数据编码边界、任务权重和后续受控实验见[50M问题分析与修正](../docs/50M问题分析与修正.md)。定时检查已关闭，之后按用户询问检查。
