## 从失败结果开始

“你好”的旧模型原始回答为“我可以让你的，我可以让你的……”。这说明保存权重、完成 SFT 和运行聊天程序都不等于模型已经能聊天。训练后必须实际提问，再依据结果判断是否需要继续改进。

本轮目标是中文单轮基础聊天：问候、自我介绍、日常提问、简单概念、简单指令和基础算术。没有承诺多轮记忆、复杂推理或通用知识可靠性。

## 数据、续训与资源

使用既有 RTX 4060 Ti、Miniconda GPU 环境及 49,558,400 参数结构；32k Tokenizer 与模板保持一致。新数据在 `D:\LubanLM-Data\chat-v2`，新日志、权重和独立账本在 `D:\LubanLM-Runs\chat-v2`。旧实验保持可复查。

中文 Wikipedia 扩展到最多 25 万篇，沿用原固定来源版本与原验证文章隔离；流式清洗、精确去重并分片编码。新增短问答来自 [BELLE train_0.5M_CN](https://huggingface.co/datasets/BelleGroup/train_0.5M_CN)，固定下载 revision，记录合成数据属性、来源许可及数据卡限制，仅进行本地实验。保留 OASST 原始树划分。自建 1,000 个候选教学样本包括 600 个规则生成并精确核算的算术样本、300 个经审阅的事实模板变体和 100 个基础聊天模板变体；不能将这些变体称为 1,000 条独立人工问答。清洗后数量以清单为准。

按规范化问题去重和分组划分；完整开发题、验收题和五道基础检查题的同文问题从 SFT 排除。相同基础知识和运算结果可以自然出现在训练中，测试检验不同问法下的回答，不能据此声称覆盖未知知识。数据清单记录剔除数与训练/验证隔离检查。

首轮累计 GPU 上限 24 小时：预训练最多 20 小时，SFT 连同候选检查最多 3 小时，最终验收预留 1 小时。预训练目标为新增 4 亿 Token，不保证在预算内全部完成。阶段目标、时间上限和能力验收是三件不同的事。

新预训练阶段通过 `--continue-from` 载入旧 Base 参数及 AdamW 状态，重置新数据采样器和阶段学习率；同一执行设置下的中断用 `--resume` 精确恢复。初始设置为序列 256、微批次 2、累积 4、BF16、峰值学习率 `3e-4`，100 步 warmup 后余弦下降。性能优化可以通过显式 `--migrate-execution` 改变计算分组及执行后端，但必须保持有效批次、训练目标、学习率进度、数据顺序和验证设置；浮点运算分组改变不能称为逐位一致。实际执行设置记录在检查点与 `reports/execution_profile.json`，对照结果见 [Win11训练效率优化](Win11训练效率优化.md)。检查点记录父权重、父 Token 与新阶段 Token，避免累计量重复计算。

每新增 2,500 万 Token 评估固定 50 万验证 Token，每 30 分钟保存可恢复的 `latest.pt`，1 亿、2 亿、3 亿 Token 另保留阶段检查点。1 亿和 2 亿阶段运行固定 5,000 条子集短 SFT，再检查开发题；末次候选也检查。短 SFT 和全部 SFT 使用 `5e-5`，只监督回答与 EOS；完整 SFT 最多两轮，独立验证集全量评估。

控制器在开发题原始输出生成后等待逐题评分。选择开发题合格率最高的 Base 候选进行完整 SFT；只有开发题达到同等门槛，才运行最终验收。任何非有限数值、验证恶化或持续重复都需要先排查，不直接靠延长训练掩盖问题。

### 后续控制器升级须知

用户已批准在最近保存点进行性能迁移，同时升级控制器。完成后以 `reports/controller_reload_pending.json` 的 `handled=true` 和实际新进程为准，无需在下一阶段再次升级。性能短测计入原预算，不能与正式训练并行。若固定验证损失比迁移前增加超过0.1，控制器保留异常权重，从不可变切换前权重回退到原执行设置，并记录重跑耗时。

性能迁移前，旧控制器尚未载入v3选择与重启恢复逻辑，原安排是在阶段审阅时升级。现已随用户批准的性能切换完成升级，`reports/controller_reload_pending.json` 的已处理记录保留供复查。后续不得为了重复升级中断正常运行的GPU训练子进程；需要修复或恢复时先核对实际进程，确认所属进程退出后再处理残留锁，保留全部GPU账本与检查点。新版入口会先处理未完成的阶段审阅，再恢复Base，后续完整SFT采用v3。

升级后核对控制器和子进程，启动绑定新PID的临时防休眠辅助进程。新控制器会将待升级记录标记为已处理，不能每次监控重复升级。

## 独立验收

题目与评分程序见 [chat_suite.py](../eval/chat_suite.py) 和 [grade_chat_suite.py](../eval/grade_chat_suite.py)。固定开发题与独立验收题各 60 道，上述六类各 10 道。开发题用于选模型，独立验收题不用于改训练数据或调参数。最终未通过时保留失败报告；下一轮更改方案后要建立新的独立验收题，不能反复针对旧题调优。

逐题阅读原始回答，记录 `relevant_readable`、`correct`、`looping` 与理由。合格回答必须相关、可读、没有循环重复，并且没有错误的核心事实或运算结果。普通问候和开放建议以是否合理回应判定，不能拿某个标准句子的关键词作机械评分。

|检查|通过条件|
|---|---|
|60 题贪心解码|整体合格率至少 80%，各类至少 60%，算术至少 80%；相关且可读至少 90%，循环重复不超过 5%|
|额外五道基础题|“你好、你是谁、Linux是什么、操作系统是什么、1+2是多少”全部合格|
|采样稳定性|固定 20 道开发题、三个种子共 60 条输出，相关且可读至少 80%，循环重复不超过 5%|
|工程交付|选定权重导出后重新加载一致，真实 CLI 能执行并保留输出|

贪心验收使用温度 0、不加重复惩罚；采样检查使用温度 0.7、top-k 40、top-p 0.9、重复惩罚 1.1，三个种子为 2026、2027、2028。最多生成 96 Token，记录 EOS、生成 ID 与循环提示。重复正则仅提示审阅，最终评分以完整答案为准。缺题、缺评分或 hash 不匹配均不得通过。

评分文件示例：

```json
{"marks":[{"id":"dev-greeting-00","seed":2026,"relevant_readable":true,"correct":true,"looping":false,"reason":"简短回应问候，没有错误自述或重复。"}]}
```

示例只展示格式；真实文件必须覆盖所有原始回答。运行 `python -m eval.grade_chat_suite --answers 原始输出.json --marks 逐题评分.json` 生成同名 `.review.json`，控制器才会继续。

## 运行与监控

```powershell
. .\scripts\chat_v2_environment.ps1

```

控制器入口为 `python -u -m scripts.train_chat_v2`。同一实验只启动一个控制器；先检查 `pipeline_status.json`、控制器/子进程和锁，存活时不重复启动。中断后检查最新有效检查点再恢复，不能删除账本后重跑。遇到残留锁，只能确认所属进程已退出后再处理。
