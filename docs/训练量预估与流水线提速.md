# 训练量预估与流水线提速

**工程预算建议：累计约50亿优质中文预训练Token，搭配约5万条独立、高质量、简短的中文聊天问答。** 可考虑的探索区间是20–100亿预训练Token、3–10万条短SFT；它们不是已经验证的充分训练阈值。当前授权目标仍是累计20亿，完成新的SFT和隔离开发评测后再决定是否扩量。没有自动把当前任务扩大到50亿。

## 为什么这样估计

|阶段|规划量|要解决的问题与决策|
|---|---|---|
|第一阶段，当前执行|累计20亿预训练Token；新增混合语料约9亿独立Token|检查新中文语料能否改善语句与语言预测；之后先做新短SFT，不用Base loss替代聊天评测|
|完整聊天尝试的预留预算|累计约50亿；约5万独立短问答，通常先完整遍历2轮|这是有希望的工程起点，仍需验证各种新问法是否能得到合适、连贯的回答|
|进一步探索上限的候选|累计50–100亿；3–10万独立短问答，按泛化效果决定轮数|只有独立聊天结果持续改善才追加；如同语料重复训练已停滞，优先修订数据和SFT分布|

预训练Token是模型处理量，独立语料Token是新增内容量，SFT条数是完整题答数量，三个量不能互换。5万条短回答若平均40–80监督Token，一轮约200–400万监督Token；完整遍历2轮约400–800万。训练总输入还包括被mask的提示，不能都算成回答监督量。

这些范围来自本项目已有失败表现、算力预算及小模型训练经验的综合判断，置信度有限。当前Chat继承的Base只有约4.08亿Token；8.08亿实验Base此前增加的是同Wiki处理量，匹配短SFT没有观察到整体聊天收益。新短SFT覆盖和语料分布很关键，不能仅增加训练时间。

[TinyStories原论文](https://arxiv.org/abs/2305.07759)证明受控词汇和故事分布下，很小的模型也可以生成连贯英语；它不是中文开放聊天的充分性证明。[SmolLM2论文](https://arxiv.org/html/2502.02737v1)通过数据对照决定混合，并强调小模型对数据噪声更敏感；其大规模英文配方也不能直接换算成本项目最低量。

“日常聊天不出错”应拆成可评测目标：回应当前问题、语句连贯、无核心常识错误、无字符乱码、无退化重复、自然结束。建议冻结至少300条新的问题作为开发评测，初步目标为合适且连贯≥90%、观察到的字符乱码0条、退化重复≤1%、96 Token内自然EOS≥98%。开发题合格之后仍需独立验收；样本内零错误不保证以后每句都正确。50M模型不能承诺开放话题的所有事实都正确。

## 哪些数据更接近目标

适合的是**通用中文语言基础 + 简单叙述/解释 + 短聊天SFT**的组合，完整数据集名称不能保证达到要求。

|部分|优先来源|处理要求|
|---|---|---|
|语言基础|[FineWeb中文v2.1高分层](https://huggingface.co/datasets/opencsg/Fineweb-Edu-Chinese-V2.1)|固定版本，图片/链接堆积、乱码、重复等过滤；系列训练对照来自v1，不把它说成v2.1已经验证本模型|
|通俗叙述和解释|[中文Cosmopedia](https://huggingface.co/datasets/opencsg/chinese-cosmopedia)的幼儿故事、中学解释|完整短文本，控制合成语料比例；公开实验的基准收益有限，不单靠它补知识|
|日常聊天与指令|[SmolTalk中文](https://huggingface.co/datasets/opencsg/smoltalk-chinese)的everyday、简单问答、完整改写|先筛选题答对应、上下文完整、身份一致、回答简短；过长答案应经教师简化并审阅，不能直接截断|
|小模型路线的补充候选|[MiniMind配套数据](https://huggingface.co/datasets/jingyaogong/minimind_dataset)|有配套小模型训练项目，但当前版本含长推理、工具调用和MiniMind身份，不直接加入本轮|

[OpenCSG技术报告](https://arxiv.org/html/2501.08197v1)包含FineWeb v1预训练和SmolTalk SFT对照，也指出Cosmopedia的同质化问题。这些是发布者的证据，尚无本项目50M上的完成要求证明。

MiniMind已按固定版本`312afb4f76391145c6902f765bb51691c09a12f5`对两个mini文件各读取2MB公开前缀，只用于预览：SFT第一条就含“由jingyaogong开发”的身份和`reasoning_content`。需要移除不适用的身份样本与推理/工具任务，重新用LubanLM模板编码，并保留完整必要历史。不能把预览当成随机全量质量验证。当前文件许可元信息包含Apache-2.0及CC-BY-NC-2.0，需按具体来源范围处理。

当前SmolTalk已下载的97,476条会话仅有一部分适合短答；此前统计的候选没有完成全量语义审查。约5万独立问答是建设目标，不是现成已通过审查的库存，不能靠复制几千条模板凑数。

## 当前资源利用与实际提速

切换前：6个物理核/12个逻辑CPU、约16GB RAM；下载时3秒采样，准备进程CPU仅约单核0.52%，全机网络接收约0.59MiB/s。4060 Ti当时利用率约2%，因为GPU还没有进入训练。原准备流程串行执行下载→清洗→编码，下载等待会阻塞CPU编码。

上一轮预训练峰值显存约2.2GB，16GB显存有余量。但更大batch并不总更快：原生交叉熵、矩阵运算、内核调度和内存访问共同决定吞吐，不能拿显存占用率当唯一优化目标。

已在父Base的独立副本上实测，模型参数不用于正式训练，原checkpoint哈希保持不变。实际包含数据取样、pinned传输、BF16、SDPA、反向、裁剪和fused AdamW更新。固定长度256，下面每项100次计时更新，另有5步热身：

|micro-batch|短测Token/小时|峰值已分配显存|与同轮batch8相比|
|---:|---:|---:|---:|
|8|9,110万|2.15GiB|1.00倍|
|16|1.358亿|3.63GiB|1.49倍|
|24|1.426亿|5.10GiB|1.56倍|
|32|1.402亿|6.57GiB|1.54倍|

首轮25步测量中，48仅约1.284亿/小时，64出现显存不足。采用24作为本轮已测配置。100步只有约8–21秒/配置，因此**上述是短吞吐基准，不是整轮已达到的持续速度，也不是收敛比较**。各batch短更新处理的Token数不同，表中副本验证loss不能比较聊天质量。

以1.426亿/小时粗算，剩余11.92亿约8.36小时；考虑验证、检查点、调度及占用，预计本轮GPU预训练约9–10小时。原预测约12小时。正式训练速度仍以本轮metrics为准。两个基准测试共用了约2.024分钟GPU，记入当前900分钟账本，未重置旧账本。

已实施：

- 4路下载预取，最多4个文件、约1.5GB窗口；下载/哈希在后台线程执行，清洗、去重、分割、写分片在主线程按原固定顺序执行。大型单文件允许独立下载，避免一次排队多个完整Cosmopedia文件。
- 每个完成文件记录下载等待与清洗/去重/编码/写入耗时，便于区分网络瓶颈和CPU瓶颈。
- 用Unicode正则统计中文比例，减少逐字符Python开销。11,901条真实源记录的筛选输出与原实现完全相同。
- 单线程/4线程预取在相同两文件上输出的Token分片哈希、数量、文档数、筛选计数完全相同；从多线程下载获得速度，不打乱样本选择。
- 批次改24、accumulation仍1，学习率仍1e-4；warmup由1000步换为334步，约205.2万Token，接近原204.8万Token。全局batch变为3倍、更新次数变少，优化轨迹不完全相同，仍须按新验证检查收敛。
- 同时补充排除`eval/suites/*.json`里冻结题的完整长问题拼写。文本分组和长串检查仍不保证语义完全无交集。

不能对下载/编码宣称固定倍数提速：原始缓存复用显著影响重建速度，网络总带宽也可能限制多线程收益。需在新文件上观察等待占比。当前先完成固定混合语料再启动GPU，便于保持验证和resume数据身份稳定；将准备与GPU训练分阶段重叠还有空间，但会增加数据版本与训练调度的复杂度，本轮尚未实施。
