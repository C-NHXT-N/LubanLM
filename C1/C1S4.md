# 1.4 本章项目成果

训练流程会为每个词表候选建立一个独立目录。目录里的文件各有用途：有的保存分词规则，有的记录特殊 Token 或训练设置。

|文件|记录内容|什么时候读取|
|---|---|---|
|`tokenizer.json`|BPE 词表与合并规则、预分词器、解码器及特殊 Token|编码、解码、保存／重载 Tokenizer|
|`tokenizer_config.json`|供 Transformers 快速分词器（fast tokenizer）加载的配置，包含特殊 Token 名称和边界符默认行为|通过 `AutoTokenizer` 加载时|
|`special_tokens_map.json`|PAD、BOS、EOS 名称与可见拼写的对应关系|把配置中的特殊 Token 名称还原为模型可识别的 Token|
|`training_config.json`|训练语料摘要、词表目标与实际大小、特殊 ID 和依赖版本|审计实验、核对模型 `vocab_size`|

评估报告单独保存在指定报告目录：`metrics.json` 适合后续程序读取，`metrics.md` 适合直接查看。模型文件和评估报告不要混为一谈：前者让相同规则可重复编码，后者说明它在某批样本上的表现。

首先在 LubanLM 根目录启动 Python，使用上一节创建的虚拟环境执行下面代码，对训练配置和 Tokenizer 本身做一次交付核对。示例读取的是上一节的小样本产物；正式选择后把 `model_dir` 改成选定候选的目录：

```python
import json
from pathlib import Path
from tokenizers import Tokenizer

# 指向含 tokenizer.json 与训练记录的同一个交付目录。
model_dir = Path("artifacts/tokenizers/demo-320")
tokenizer = Tokenizer.from_file(str(model_dir / "tokenizer.json"))
training = json.loads((model_dir / "training_config.json").read_text(encoding="utf-8"))

# 必须包含 added tokens，否则 PAD/BOS/EOS 可能没有计入模型词表。
vocab_size = tokenizer.get_vocab_size(with_added_tokens=True)
special_ids = {token: tokenizer.token_to_id(token) for token in ("<pad>", "<bos>", "<eos>")}
assert vocab_size == training["actual_vocab_size"]
assert special_ids == training["special_token_ids"]
print(vocab_size, special_ids)
```

`with_added_tokens=True` 会把额外加入的特殊 Token 也计入总数。模型的 Embedding 为每个 ID 存一行向量，因此这个总数才是要写入模型配置的 `vocab_size`。只读取 BPE 模型内部的词表，可能漏掉后来添加的特殊 Token。当前训练器依次加入 `<pad>`、`<bos>`、`<eos>`，样例中的 ID 是 0、1、2。分词器、Embedding、输出词表和特殊 Token 配置必须使用同一套编号；训练后不能重新排序或随意增删 Token，否则模型参数矩阵中的行就会对应到错误的 Token。

三个特殊 Token 各自表示一种结构信息。**BOS**（beginning of sequence，序列开头）标记输入从哪里开始；**EOS**（end of sequence，序列结尾）标记内容结束，生成程序可以把它当作停止信号；**PAD**（padding，填充）是为了让不同长度的序列能放进同一个批次而补上的占位符。PAD 既不表示文本结束，也不是普通空格。批量训练时还要告诉模型哪些位置是 PAD，本节先确认它的 ID 和用途。

普通文本编码不自动附加 BOS、EOS。只有样本格式明确需要边界符时才显式加入，而且不能把已经存在的边界符重复加一遍。配套辅助函数 `encode_text` 在 [tokenizer_utils.py](program/1.3/tokenizer_utils.py) 实现了这个检查；核心操作如下：

```python
text = "Linux 是一个操作系统"
bos_id = tokenizer.token_to_id("<bos>")
eos_id = tokenizer.token_to_id("<eos>")
# 先编码正文，不让 Tokenizer 自动补边界符。
ids = tokenizer.encode(text, add_special_tokens=False).ids
# 若正文已有可见的 BOS，保持它不重复添加。
if not ids or ids[0] != bos_id:
    ids.insert(0, bos_id)
# EOS 标记样本结束；不能用 PAD 代替。
if not ids or ids[-1] != eos_id:
    ids.append(eos_id)
```

其中 `<bos>` 和 `<eos>` 的 ID 应通过 `token_to_id` 查询，或读取前面已经核对的 `special_ids`，不要猜编号。解码时还要决定是否保留特殊 Token：`skip_special_tokens=False` 会把 BOS/EOS 显示为它们的拼写；设为 `True` 则会在返回文本时略去这些结构标记。只展示正文时通常略去它们；排查模型是否生成了边界符时则应保留。

例如，对 `Linux 是一个操作系统` 添加 BOS 和 EOS，编码序列的首尾应分别为 ID 1 和 ID 2；把序列解码并跳过特殊 Token 后，结果应与原文完全相同。PAD 不应被拿来替换 EOS；遇到批次补齐时，要另外按 PAD ID 添加占位。

本章还提供字节级往返检查，在 LubanLM 根目录和同一虚拟环境中运行：

```powershell
python C1\program\1.4\smoke_test.py
```

它会检查中文、英文、C/C++ 片段、连续空格、换行、缩进、emoji、空文本、较长文本，以及边界符是否重复添加；训练候选、重载 JSON 文件和逐类别评估也包含在内。若环境安装了 Transformers，还会通过 `AutoTokenizer.from_pretrained` 再做一次加载和往返检查。字符级和教学 BPE 则验证未见字符会明确报错。这样的检查回答的是“产物能否按相同规则复用”，不能代替正式语料上的效果评估。

交给第 2 章的是所选目录以及从中读取的 `vocab_size`、`bos_token_id`、`eos_token_id`、`pad_token_id`，不是目标词表大小的口头约定。2026-10-02 已完成有界教学语料上的 16K、32K、40K 对照，主流程实际采用 32,000，PAD/BOS/EOS 为 0/1/2。正式目录为 `$env:LUBAN_DATA\tokenizers\vocab-32000`，完整来源与诊断见第 4 章及 Windows 实跑报告。这里的 demo-320 仍是小样本演示，不能与正式权重交换。
