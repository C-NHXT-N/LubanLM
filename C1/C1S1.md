# 1.1 从文字到 Token

这一节要完成一件具体的事：把人能读懂的文本变成一串整数，再用这串整数还原原文。语言模型接收的是整数序列。Tokenizer（分词器）负责把文本切成较小的片段，再把每个片段映射为 Token ID（编号）。读懂“文本→片段→编号”这条转换链，后面看到 Embedding、模型输入和词表配置时，就能知道它们如何对应。

先用课程目录中的例子：

```python
text = "Linux 是一个操作系统"
# 按 Unicode 字符拆分；空格也会保留在列表中。
characters = list(text)
print(characters)
print(len(characters))
# split() 仅按空白切分，用来观察它对中英文混合文本的局限。
print(text.split())
```

`list(text)` 按 Python 字符串中的字符拆分，输出 13 个字符：`['L', 'i', 'n', 'u', 'x', ' ', '是', '一', '个', '操', '作', '系', '统']`。中间的空格也在序列里。`text.split()` 默认按连续空白切分，结果却是 `['Linux', '是一个操作系统']`：英文单词有空格边界，中文词之间通常没有。代码语言也不一定用空格分开逻辑单位，例如 `std::vector<int>`。所以“按空格切出单词”不能作为适用于中英文和代码的通用分词方案。

另一种极端是把每个字符直接作为 Token。它不会遇到“整词没有进词表”的问题，但序列较长；而且字符范围很大，普通字符集之外还有 emoji、罕见字及代码符号。完整单词方案能让常见词更短，却必须处理没有见过的词。实际分词器常使用介于两者之间的子词（subword）：常见片段可以合成一个 Token，未见过的词则拆成已知片段。比如 `operating` 可能是一个 Token，也可能拆成 `oper` 和 `ating`；`操作系统` 也可能拆成 `操作` 和 `系统`。具体切法取决于分词器，不应凭例子推断正式词表的结果。

为了手动完成编码，暂时规定一套**仅用于本例**的切分：

```text
原文：Linux 是一个操作系统
Token：["Linux", " ", "是", "一个", "操作", "系统"]
```

注意，`" "` 是独立的空格 Token。省略它便无法准确还原原文。接着建一个小词表，每个 Token 对应一个整数：

|Token|Token ID|
|---|---:|
|`Linux`|0|
|空格 ` `|1|
|`是`|2|
|`一个`|3|
|`操作`|4|
|`系统`|5|

用 Python 字典表达这种对应关系，并按 Token 顺序查出 ID：

```python
tokens = ["Linux", " ", "是", "一个", "操作", "系统"]
# enumerate 同时给出下标和 Token，下标就是本例的 Token ID。
vocab = {token: token_id for token_id, token in enumerate(tokens)}
# 这里 tokens 已手工切好；真实 Tokenizer 会先执行切分规则。
ids = [vocab[token] for token in tokens]
print(ids)  # [0, 1, 2, 3, 4, 5]
```

这里的 `vocab` 把字符串映射到整数；真实分词器先决定文本如何拆分，再为拆出的 Token 查 ID。还原时需要反向查表：

```python
# 建立与 vocab 方向相反的映射，供 ID 查回 Token。
id_to_token = {token_id: token for token, token_id in vocab.items()}
# 按原 ID 顺序拼接，空格 Token 因此不会丢失。
reconstructed = "".join(id_to_token[token_id] for token_id in ids)
print(reconstructed)  # Linux 是一个操作系统
assert reconstructed == "Linux 是一个操作系统"
```

现在可以区分几个容易混淆的词：字符、单词和子词描述文本可能具有的不同切分粒度；Tokenizer 实际切出的片段叫 Token；Token ID 是词表中对应的编号；词表（vocabulary，简称 vocab）保存 Token 与 ID 的映射。分词器对同一文本切法不同，得到的 ID 序列也会不同，因此解码必须使用编码时的同一套映射。编号只是查表用的索引：把 `Linux` 从 ID 0 改成 17，本身不会改变它的词义；但若模型仍按旧映射训练或加载，ID 17 就会查到错误的那一行，模型读到的内容也会错位。

词表里不同 Token 的总数叫 `vocab_size`。本例有 6 个普通 Token，所以示例词表大小是 6；它还没有 PAD、BOS、EOS 等特殊 Token，正式配置会在 [1.4](C1S4.md) 说明。模型会为每个 Token ID 存一行向量，这张表叫 Embedding（嵌入表）。设每行有 4 个数，词表有 6 个 Token，那么 Embedding 矩阵形状是 `6 × 4`，共含 24 个可训练参数；若词表增至 13 个，矩阵变为 `13 × 4`，共含 52 个参数。通用计算为：

```text
Embedding 参数量 = vocab_size × hidden_size
```

若模型把输入 Embedding 和输出 LM Head 的权重分开保存，输出矩阵也会随词表扩大；若权重共享，就不能把它当成另一份独立参数再加一次。这里先只计算输入 Embedding，完整模型规格在第 2 章讨论。

切分粒度也会影响序列长度。按字符切分，这句话有 13 个位置；本例手工切分后有 6 个位置。同一段原文切成较少 Token，模型要处理的位置就更少；但词表每增加一个 Token，Embedding 就要多存一行向量。选择词表大小时，要同时考虑不同语种和代码的 Token 数、词表带来的参数开销，以及训练效率，不能只追求更短的序列或更大的词表。16K、32K 和 40K 的比较放在 [1.3](C1S3.md)，本节这 6 个 Token 只用于演示查表。

把例句换成“Linux 是一个系统”，可以继续用同一词表得到 `[0, 1, 2, 3, 5]`；换成“Linux 很好”却找不到“很好”对应的条目。这说明手工指定几个 Token 不能覆盖新文本。[下一节](C1S2.md)先从训练文本收集字符，再用 BPE 自动学习常见片段的合并规则。
