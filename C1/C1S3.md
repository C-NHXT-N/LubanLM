# 1.3 训练 LubanTokenizer

本节要训练自己的 LubanTokenizer，而不是直接使用 Qwen3 的 Tokenizer。我们先准备少量训练文本，再配置字节级 BPE 并跑通整个流程，最后说明如何比较 16K、32K 和 40K 三种词表目标。当前仓库只有教学样本，还没有选定正式预训练数据集；因此，下面的小样本结果只能检查程序流程，不能用来决定最终词表大小。

**先确定文本从哪里来。** 教学顺序仍是 Tokenizer→Transformer→Corpus，但准备工作要先大致选出可能用于预训练的数据。分词器会从文本中学习常见片段，所以应尽量使用接近未来训练内容的样本。现在只需从候选数据中抽取一小部分来训练；第 4 章再比较数据集、清洗完整语料并制作训练分片。

抽样可以按以下过程操作：

1. 记录每个候选数据的名称、来源、版本、正文所在字段和使用许可。先看几条原始记录，确认文本字段确实是正文。优先从计划用于预训练的主要数据中抽样；只有确有需要时，再加入一个补充来源。
2. 从记录中提取正文，去掉空文本和完全重复的记录，同时保留代码缩进、换行等原始字符。抽样比例应接近后续训练文本的实际组成，不要默认中文、英文和代码必须各占三分之一。
3. 固定并记录抽样随机种子和样本数。先按完整文档划分训练集和评估集，再导出 JSONL（每行一条 JSON 记录的文本文件）。不要把同一文档的片段或重复文本分到两边，否则评估时可能遇到训练中已经见过的内容。评估集应分别包含中文、英文和代码；缺少某一类，就无法从报告判断分词器对该类的表现。
4. 将小样本文件保存为 `data/tokenizer/train.jsonl` 和 `data/tokenizer/validation.jsonl`，并记录来源、抽样方法和分类规则。这两个文件需要自行准备，仓库当前没有提供正式候选语料。比较不同词表大小时，要让所有候选使用同一组文件。

JSONL 每行包含正文 `text` 和类别 `category`。类别只用于把评估结果分组查看，不会送进模型。混合多种语言的文档按主要内容标注即可；这是便于观察的粗分类，不是精确的语言比例统计。当前训练程序会把文件内容读入内存，所以这里只使用本机内存能容纳的小样本，不要直接把完整预训练数据集交给它。

**从字符转向字节。** 上一节的 BPE 从 Unicode 字符开始。如果训练文本里没有某个字符，字符级方法就无法表示它。项目改用 ByteLevel BPE：先把文本编码成计算机存储用的 UTF-8 字节，再把每种可能的字节映射到固定的 256 种基础符号。比如“你”对应字节 `E4 BD A0`，即使训练文本没出现过“你”，这三个字节符号仍然存在。接着，BPE 可以把常见的相邻字节片段合并成较大的 Token。ByteLevel 说明文本如何变成基础符号；学习合并规则仍然使用上一节的 BPE。

还有几个组件共同决定处理细节。预分词器（pre-tokenizer）先把原文切成较小片段，BPE 再在每个片段内部学习合并规则。本项目使用 `ByteLevel(add_prefix_space=False, use_regex=True)`：`use_regex=True` 按内置规则划分基本片段，避免 BPE 任意跨越片段合并；`add_prefix_space=False` 表示不要在文本开头自动补空格。Tokenizer 没有设置文本归一化（normalizer），也就是不会主动改大小写或转换 Unicode 字符形式。解码器（decoder）负责把内部的字节表示重新还原成 UTF-8 文本。训练完成后，要检查空格、连续空格、换行、缩进和特殊字符能否原样还原。

训练器把 256 种字节符号作为起始词表，并按顺序加入 `<pad>`、`<bos>`、`<eos>` 三个特殊 Token。目标 `vocab_size` 是最终词表总数，包含起始字节、合并得到的 Token 和特殊 Token，所以最小值是 259。脚本把 `min_frequency`（最低出现次数）设为 2：只有在训练文本中至少出现两次的相邻片段，才有资格成为合并候选。这样可以过滤只偶然出现一次的组合。如果符合条件的合并数量不够，训练器会提前停止，实际词表便小于目标值；后续参数计算要使用实际词表大小。

训练／评估输入为 UTF-8 JSONL，每行包含 `text` 和 `category`。类别只能是 `中文`、`英文` 或 `代码`，用于分别统计覆盖效果。下面是[附带样例语料](program/1.3/sample_train.jsonl)中的记录格式；示例很小，只能检查流程：

```json
{"text":"Linux 是一个操作系统。","category":"中文"}
{"text":"Linux is an operating system.","category":"英文"}
{"text":"int main() { return 0; }","category":"代码"}
```

训练集学习合并规则，独立评估集用来测量规则在未参与训练的文本上的表现。两者不能使用同一批文本，否则报告不能说明候选对新文本是否有效。正式训练集应覆盖后续预训练语料中的主要中文、英文和代码类型，评估集也要分别包含这几类；数量很多但只集中在一种文本上的语料，仍可能得到偏向该类别的词表。

在仓库根目录使用 D 盘 Miniconda 环境，再用小样本训练一次 320 Token 目标的候选。环境首次建立见附录 B，已有环境直接选择：

```powershell
# 选择已安装的 D 盘独立环境，缓存也放在 D 盘。
. .\scripts\workspace_env.ps1
python -m pip install -r C1\program\1.3\requirements.txt
python C1\program\1.3\train_tokenizer.py --input C1\program\1.3\sample_train.jsonl --vocab-size 320 --output artifacts\tokenizers\demo-320
```

训练脚本从 JSONL 逐行读取文本，创建 BPE 模型、ByteLevel 预分词器和解码器，再调用 `BpeTrainer` 学习合并规则并将结果保存到指定目录。`special_tokens` 固定特殊 Token 的顺序；`initial_alphabet` 提供全部字节符号；`vocab_size` 限制词表总量；`min_frequency` 决定一个组合至少出现几次才参与合并。输出的训练配置会记录语料文件的 SHA-256（用于核对文件内容是否改变）、样本数、目标和实际词表大小、特殊 Token ID 及依赖版本，方便之后复查实验设置。若输出显示“实际 317 / 目标 320”，表示这份小语料只产生了 58 个符合频次条件的合并：256 个基础符号 + 3 个特殊 Token + 58 个新 Token，共 317 个。程序不会为了凑数把词表补到 320。

程序中最关键的顺序是先指定处理规则，再让训练器读取文本：

```python
# 不设置 unk_token：字节基础字母表负责表示任意 UTF-8 文本。
tokenizer = Tokenizer(models.BPE(unk_token=None))
tokenizer.pre_tokenizer = pre_tokenizers.ByteLevel(add_prefix_space=False, use_regex=True)
tokenizer.decoder = decoders.ByteLevel()
trainer = trainers.BpeTrainer(
    vocab_size=args.vocab_size,
    min_frequency=2,
    special_tokens=list(SPECIAL_TOKENS),
    initial_alphabet=pre_tokenizers.ByteLevel.alphabet(),
    show_progress=True,
)
# 生成器只传入 text；category 留给后续分组评估。
tokenizer.train_from_iterator((record["text"] for record in records), trainer=trainer, length=len(records))
```

这是[完整训练程序](program/1.3/train_tokenizer.py)中的片段，不是独立脚本。`records` 是由 JSONL 读出的字典列表，生成器每次只把 `text` 交给训练器；类别不参与 BPE 训练。BPE 模型保存合并规则，预分词器规定合并边界，解码器规定如何还原字节，三者一起写进 `tokenizer.json`，加载时才能复现同样的编码。

接着在未参与训练的样例集上运行评估：

```powershell
# --hidden-size 只用于计算 Embedding 参数量，不改变 Tokenizer 本身。
python C1\program\1.3\evaluate_tokenizer.py --tokenizer artifacts\tokenizers\demo-320 --input C1\program\1.3\sample_eval.jsonl --report-dir artifacts\reports\demo-320 --hidden-size 64
Get-Content artifacts\reports\demo-320\metrics.md
```

评估器会先把每条原文编码成 Token ID，再从 ID 解码回文本，并逐字比较解码结果与原文。空格、换行、emoji 或代码缩进只要有变化，`roundtrip_ok`（往返还原是否成功）就会显示失败。报告还会按类别统计 Token 总数，以及每个 Token 平均覆盖多少字符和 UTF-8 字节：

```text
字符数 / Token = 该类别全部文本的字符数总和 ÷ Token 数总和
字节数 / Token = 该类别全部文本的 UTF-8 字节数总和 ÷ Token 数总和
Embedding 参数量 = 实际词表大小 × hidden_size
```

在同一份文本上，同类别每个 Token 平均覆盖更多字符，通常表示切分得更紧凑。不过中文和英文字符占用的 UTF-8 字节数不同，所以字符／Token 和字节／Token 要分开看；还要同时查看该类别的 Token 总数，不能只凭一个比值判断整体效果。若评估集没有 Token（例如其中有空文本），程序会把比值记为 0；这不表示词表表现更好。`hidden_size=64` 只用于本次小实验的参数估算，不是 LubanLM 的模型规格。

这次程序实测使用 6 条样例训练文本、4 条样例评估文本，结果如下：

|评估类别|记录数|字符数总和|UTF-8 字节总和|Token 总数|字符／Token|字节／Token|往返还原|
|---|---:|---:|---:|---:|---:|---:|---|
|中文（含一条空文本）|2|28|65|58|0.4828|1.1207|通过|
|英文|1|57|57|48|1.1875|1.1875|通过|
|代码|1|33|33|27|1.2222|1.2222|通过|

实际词表大小为 317，样例报告中的 Embedding 参数量为 `317 × 64 = 20,288`。这些数字能核验训练、评估、计算和解码流程；样本不足以达到目标，内容也不代表预训练语料，所以不能据此推断正式词表哪档最好。

正式实验需用同一份训练集和同一份独立评估集训练三个候选，保持 Tokenizer 版本、类别划分及 `min_frequency` 一致，只改变目标词表大小。配套 PowerShell 脚本依次运行 16K、32K、40K，并为每个候选写独立报告：

```powershell
# 三档候选读取同一组训练/评估文件，只有目标词表大小不同。
powershell -ExecutionPolicy Bypass -File C1\program\1.3\run_vocab_sweep.ps1 `
    -TrainFile 'data\tokenizer\train.jsonl' `
    -EvalFile 'data\tokenizer\validation.jsonl' `
    -HiddenSize 1024 `
    -OutputRoot '.\outputs\vocab-sweep'
```

2026-10-02 的正式有界教学样本结果已填入下表；配套脚本默认附带的小语料只做演示，正式运行必须传入真实路径。这里 K 按十进制千计，16K、32K、40K 分别是 16,000、32,000、40,000。Embedding 参数列是**实际词表达到目标时**、按第 2 章两种候选隐藏维度计算的输入矩阵参数；若模型不共享 LM Head 权重，输出矩阵还有相应参数。`--hidden-size` 只改变报告中的参数估算，不影响 Tokenizer 的训练或切分。

|目标词表|中文 Token 总数|英文 Token 总数|代码 Token 总数|实际词表大小|Embedding 参数 H=512 / H=1024|
|---:|---:|---:|---:|---:|---:|
|16,000|281,565|31|35|16,000|8,192,000 / 16,384,000|
|32,000|260,832|26|32|32,000|16,384,000 / 32,768,000|
|40,000|254,745|25|28|40,000|20,480,000 / 40,960,000|

选型时先排除往返失败的候选，再比较各类文本的 Token 总数和参数开销。例如词表从 16K 增加到 32K，在 H=512 时多出 8,192,000 个输入参数；如果 Token 数仅略降，就要考虑这部分预算是否更适合模型其他模块。切分更紧凑也不直接证明问答质量更高，不能仅靠 Tokenizer 报告宣布某档词表最优。

词表学习可以先用有界训练侧片段完成，不必等全部 Corpus 编码。本次已经选定实际 32,000，因而第 2 章的 32,000 规格计算仍适用；两种模型共用同一套 LubanTokenizer，词表或特殊 ID 改变时重新核对配置。完整训练代码见[训练脚本](program/1.3/train_tokenizer.py)，评估代码见[评估脚本](program/1.3/evaluate_tokenizer.py)；交付核对方法放在 [1.4](C1S4.md)。

训练器参数可查阅 Hugging Face 的 [BpeTrainer 文档](https://huggingface.co/docs/tokenizers/main/api/trainers)。本节程序固定使用 `tokenizers==0.22.2`，以配套程序在该版本的实际输出为准。

本次三组词表使用同一份训练侧有界片段，共 14,401 条、6,463,443 字符；评估包含 100 篇独立中文文章及各一条自编英文、代码诊断。三组往返还原全部通过，主流程选择实际 32,000 词表。它不是多语种语料配比实验，也不据此宣称 32k 最优。完整命令、内存限制调整与原始报告见 [第 4.3 节](../C4/C4S3.md) 和 [Windows 实跑报告](../docs/Windows实跑报告.md)。原样例 demo-320 仍只承担流程教学。
