# 4.4 构建 LubanCorpus-v1

> 2026-10-16 路线更新：50M 已完成 5B Token 预训练及一轮 SFT，作为从零训练的教学案例保留；现有结果未证明可靠通用问答能力。第7章起转向成熟模型 LoRA 微调与部署，扩容另作可选实验。当前状态见 [项目状态](../PROJECT_STATUS.md)。

这一节把前三节得到的文件连成一份数据说明。假设别人只拿到一个很大的 `.bin`，他还不知道它来自哪些文章、用了哪个词表、每个整数占几字节。数据版本需要同时交付内容与解释，而不是仅把文件夹改名为 `v1`。

本次版本标记为 `LubanCorpus-v1-teaching`。`teaching` 表明它是有界课程样本：Wikipedia 中文文章用于预训练，OASST 中文父子问答用于 SFT。训练侧与验证侧分开保存，英文和代码的少量自编例句属于 Tokenizer 诊断，不能算入预训练语料配比。

在项目根目录运行以下只读检查：

```python
from scripts.common import DATA, RUNS, read_json

stats = read_json(RUNS / "reports/data_stats.json")
tokens = read_json(RUNS / "reports/tokenization_stats.json")
manifest = read_json(DATA / "processed/pretrain-train/manifest.json")
print(stats["wiki"]["split_documents"])
print(tokens["train"])
print(manifest["dtype"], len(manifest["shards"]))
assert sum(row["tokens"] for row in manifest["shards"]) == manifest["tokens"]
```

这里核对的是同一个版本内部的数量关系。`documents` 表示文章数，`tokens` 表示编码后的位置总数，两者不能互换。一篇长文章和一篇短文章都计作一篇，却可能相差上千个 Token；用文档数估算训练时间很容易误判。

长度统计至少保留字符数的最短、中位数、最长值，以及编码后的平均文档 Token 数。字符长度主要帮助查看原文，Token 长度决定模型计算成本。还要记录过滤原因、去重方式、划分方法和样本来源。当前精确去重不保证清除改写文本，顺序取前 30,000 篇也不保证均衡抽样，数据说明应如实写清。

`sources.yaml` 把来源元信息集中保存；JSON 报告供程序读取。原始记录保留文章 URL 和编号，可以追溯具体内容。模型导出目录以后不需要附带全部原始文章，但模型说明必须指向这个数据版本和 Tokenizer 哈希，否则无法确定权重到底对应哪张词表。

训练预算与数据总量也要区分。比如训练集有两千万 Token，而本次预算只允许处理八百万 Token，模型没有读完全部数据；随机窗口还可能再次读到同一位置。报告中的 `input_tokens` 表示训练实际处理的输入位置数，不是去重后的独立知识量，也不意味着完整遍历了语料。

实际统计与处理日志集中在 [Windows 实跑报告](../docs/Windows实跑报告.md)。若运行记录显示某个步骤失败，应先处理失败再启动训练，不能靠一个版本名称绕过数据检查。现在数据已经具备来源、格式、划分和可读取的整数文件，第 5 章可以把批次交给模型，并算出一次预测离真实下一个 Token 有多远。
