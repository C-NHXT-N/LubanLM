# 2.4 设计 50M 与 0.5B 模型规格

> 路线说明：50M是从零训练教学对象；0.5B保留为结构规格和参数量对照，不要求正式训练，也不是第7章成熟模型的权重来源。

上一节接好了一个 Block。现在要决定每个向量有多宽、堆叠多少层，并据此算出模型要存多少可训练数字。50M 和 0.5B 使用同一套代码，只改变这些尺寸；M 表示百万，B 表示十亿，名称是近似规模，不要求总数恰好等于 50,000,000 或 500,000,000。这里规模名称中的 B 与张量形状里表示批量大小的 B 无关。

先区分两类“参数”。JSON 中的 `hidden_size=512` 是配置，告诉程序每个隐藏向量有 512 个特征；它不会被训练改成 513。Embedding、投影矩阵和归一化缩放向量里的数字才是可训练参数，它们在训练中被更新。本节统计后一类数字的总数。

沿用 C1 的小词表，如果有 6 个 Token、每行向量有 4 个数，Embedding 就有 `6×4=24` 个可训练参数。一般地，词表大小记为 `V_vocab`，隐藏宽度记为 H，输入表包含 `V_vocab×H` 个数。为了保留原有参数公式，下文公式中的 V 均指词表大小，也就是 `V_vocab`，不指 Attention 的 Value 张量。

完整模型还需要以下尺寸，它们在配置文件中都有对应字段：

|配置项|符号|决定什么|
|---|---|---|
|`vocab_size`|`V_vocab`|输入表行数和每个位置的输出分数个数，包含特殊 Token|
|`hidden_size`|H|Block 外部每个位置的特征数|
|`num_hidden_layers`|L|堆叠的 Block 数量|
|`num_attention_heads`|`n_q`|每层 Query 头数|
|`num_key_value_heads`|`n_kv`|每层 K/V 头数|
|`head_dim`|d|每个头的特征数|
|`intermediate_size`|I|SwiGLU 两条支路的中间宽度|
|`context_length`|`T_max`|候选配置允许的最大输入长度|

本课程要求 `H=n_q×d`，使头拼接后回到 H；`n_q` 能被 `n_kv` 整除，使 Query 头能分组；d 为偶数，使 RoPE 坐标能两两配对。这些是本课程实现采用的约束，并不表示所有 Transformer 都必须如此设置。

先不急着代入大模型数字，从一个模块开始数。一个 `[H,I]` 矩阵有 H 行、I 列，共 HI 个数；SwiGLU 的 gate、up 各有这样一份，down 的 `[I,H]` 也有 HI 个数，所以合计 3HI。类似地，Attention 的 Q 与输出投影分别有 `Hn_qd` 个数，K、V 分别有 `Hn_kvd` 个数。

下面仍按“输入行向量乘矩阵”的方式写权重形状。PyTorch 的 Linear 通常按 `[输出维,输入维]` 保存权重，与表中投影矩阵互为转置，但元素数量相同。本节候选的线性层没有偏置，RMSNorm 只学习缩放向量：

|模块|权重形状|参数个数|
|---|---|---:|
|Embedding|`[V_vocab,H]`|`V_vocab×H`|
|每层 Q 投影|`[H,n_q*d]`|`Hn_qd`|
|每层 K、V 投影|各为 `[H,n_kv*d]`|合计 `2Hn_kvd`|
|每层 Attention 输出投影|`[n_q*d,H]`|`Hn_qd`|
|每层 gate、up、down|`[H,I]`、`[H,I]`、`[I,H]`|合计 `3HI`|
|每层两个 Block RMSNorm|各为 `[H]`|合计 `2H`|
|每层 Q/K RMSNorm|各为 `[d]`|合计 `2d`|
|Final RMSNorm|`[H]`|H|
|LM Head|独立时 `[H,V_vocab]`；共享时复用 Embedding|独立时 `V_vocab×H`；共享时不新增|

Q/K Norm 各自的 d 维向量在对应类型的头之间共享，因此是 2d，不再乘头数。输出头是否新增参数，则由 `tie_word_embeddings` 决定：设输入表为 E，输入时按 ID 查行，输出时用同一个 E 的转置计算词表分数。真正共享时只存一份可训练参数，不是复制两份初值相同的矩阵。输出乘法仍要执行，只是不另存一份权重。两个候选都设置 `tie_word_embeddings=true`。

按表把每层的 Attention、前馈网络和归一化分别相加，得到：

$$
P_{\mathrm{attn}}=2Hd(n_q+n_{kv}),\qquad
P_{\mathrm{ffn}}=3HI,\qquad
P_{\mathrm{norm/block}}=2H+2d.
$$

P 表示参数个数。第一项里的两个系数 2 分别对应 Q 与输出投影、K 与 V 投影；第二项的 3 对应 gate、up、down；第三项包含两个 H 维 Norm 与两个 d 维 Norm。再乘层数 L，加上输入表和最终 Norm，共享权重时总量为：

$$
P_{\mathrm{total}}=VH+L\left[2Hd(n_q+n_{kv})+3HI+2H+2d\right]+H.
$$

这里 V 就是前面定义的 `V_vocab`。不共享时再加一份 VH。RoPE、Softmax、SiLU、残差加法和因果遮罩在当前实现中没有额外可训练参数，预先生成的正弦、余弦表也不计入权重数量。

现在代入 50M 候选。先取 `H=512,I=1536,n_q=8,n_kv=2,d=64`，一层 Attention 有 `2×512×64×(8+2)=655,360` 个参数，前馈网络有 `3×512×1536=2,359,296` 个，归一化有 `2×512+2×64=1,152` 个。一层共 3,015,808 个。若词表暂取 32,000，输入表已经有 16,384,000 个，堆叠 11 层后为：

```text
16,384,000 + 11 × 3,015,808 + 512 = 49,558,400
```

这解释了怎样从单层成本估算层数，不证明 11 层效果最好。C1 后续已完成教学语料上的词表对比，主流程实际词表为 32,000，所以本节这组参数量仍适用。2048 是配置容量，本次主要预训练窗口为 256，不代表长文本质量或 RKLLM 支持已经验证。两种候选及计算结果如下：

|配置或计算项|LubanLM-50M 候选|LubanLM-0.5B 候选|
|---|---:|---:|
|vocab_size（暂定）|32,000|32,000|
|hidden_size|512|1024|
|num_hidden_layers|11|30|
|num_attention_heads|8|16|
|num_key_value_heads|2|4|
|head_dim|64|64|
|intermediate_size|1536|4096|
|context_length（暂定）|2048|2048|
|每层 Attention 参数|655,360|2,621,440|
|每层 FFN 参数|2,359,296|12,582,912|
|每层 Norm 参数|1,152|2,176|
|Embedding 参数|16,384,000|32,768,000|
|全部 Block 参数|33,173,888|456,195,840|
|Final RMSNorm 参数|512|1,024|
|总参数量（共享 LM Head）|49,558,400|488,964,864|
|若不共享 LM Head 的总量|65,942,400|521,732,864|

配置文件是 [config_50m.json](program/2.4/config_50m.json) 和 [config_0.5b.json](program/2.4/config_0.5b.json)。它们指定本课程模型的尺寸，尚不是完整的 Hugging Face/RKLLM 标准模型目录；只把某个 `model_type` 字段改成 `qwen3`，并不能完成转换适配。

在 LubanLM 根目录的 PowerShell 中执行[参数计算程序](program/2.4/count_parameters.py)，可以按模块复算。它只用 Python 标准库，不创建模型，也不占用 GPU：

```powershell
python C2\program\2.4\count_parameters.py
```

不传参数时，脚本读取两份候选 JSON，先检查尺寸关系，再统计各矩阵。以下片段说明总量如何累加，完整程序会另外列出 Q、K、V 与输出投影的数量：

```python
attention = 2 * hidden * head_dim * (query_heads + kv_heads)
ffn = 3 * hidden * intermediate
block_norm = 2 * hidden + 2 * head_dim
blocks = layers * (attention + ffn + block_norm)
embedding = vocab * hidden
# 共享输出头不另加参数；最后的 hidden 对应 Final RMSNorm。
lm_head_extra = 0 if config["tie_word_embeddings"] else embedding
total = embedding + blocks + hidden + lm_head_extra
```

接着只改变词表，观察它怎样影响参数预算：

```powershell
python C2\program\2.4\count_parameters.py --vocab-size 16000
python C2\program\2.4\count_parameters.py --vocab-size 40000
```

这两条命令只覆盖计算中的 `V_vocab`，不改其余尺寸，也不覆盖原 JSON。共享权重时每增加一个 Token，50M 增加 512 个参数，0.5B 增加 1024 个。词表为 16,000 时，总量分别为 41,366,400 和 472,580,864；为 40,000 时，分别为 53,654,400 和 497,156,864。词表变大不仅改变分词器文件，也直接占用模型的参数预算。

如果已运行 C1.3 的演示，还可以让程序读取真实生成的词表：

```powershell
python C2\program\2.4\count_parameters.py --tokenizer artifacts\tokenizers\demo-320
```

它从 `tokenizer.json` 收集实际 ID，包含额外添加的 Token，再与 `training_config.json`、`tokenizer_config.json` 中的记录核对。目标大小 320 不一定就是实际大小，因此不能仅从目录名确定参数量。这个命令演示跨章读取；正式选定 Tokenizer 后，应换成正式目录，并据真实词表大小和特殊 ID 更新配置。只计算一份自定义配置时用 `--config 路径`；`--vocab-size` 与 `--tokenizer` 二选一，前者做假设比较，后者读取实际产物。

参数总数还不能直接回答训练需要多少显存。训练除权重外还要存梯度、优化器状态和中间激活；批量、序列长度、精度及注意力实现都会改变开销。增大上下文长度虽然不增加标准 RoPE 的可训练位置表，却会增加注意力中间数据和生成缓存。因此是否能在 16GB 显存中训练，需要在具体设置下实测。

至此可以把两份尺寸配置交给[第 3 章](../C3/C3S1.md)的同一套实现，并用实际参数对象复核手算。字段含义可对照 [Qwen3 配置文档](https://huggingface.co/docs/transformers/v5.8.0/model_doc/qwen3)，本课程只采用已讲解的结构。若选择完整 RK3576 路线，正式长期投入前还应完成 C3.4 的转换尝试；本次 Windows 50M 教学路线只验证标准目录映射与重新加载，RKLLM 转换仍未执行。
