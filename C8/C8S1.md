# 8.1 从 Logits 到下一个 Token

模型、环境与目录见[教材基准](../docs/教材基准.md)；历史任务结果见[教学案例](../docs/cases/2B任务适配分析.md)，当前数据状态以[项目状态](../PROJECT_STATUS.md)为准。

第7章评测并合并成熟模型后，推理时先把用户问题变成训练时相同的前缀，再调用 `forward`。一次前向返回 `[B,T,V_vocab]` 的分数；生成下一个 Token 只看当前最后一个位置，因为它已经看过整个可见前缀。

先用三候选的教学分数：

```python
import torch

logits = torch.tensor([2.0, 0.0, -1.0])
print(logits.softmax(dim=-1))
print(int(logits.argmax()))  # 0
```

softmax 把分数变成约 `[0.8438,0.1142,0.0420]` 的概率。greedy 解码选择最大分数的候选，因此选 ID 0；softmax 不改变候选的排序，所以这一步可以直接对 logits 做 `argmax`。

成熟模型的词表大小从其配置读取，不能写死为32,000。以下先用原生50M接口回看一轮预测，32K词表只属于这个教学例子；示例接在已有的 `model`、`tokenizer` 与设备选择之后，不负责加载Qwen：

```python
ids = tokenizer.encode(text, add_special_tokens=False).ids
x = torch.tensor([ids], dtype=torch.long, device=device)
with torch.no_grad():
    scores = model(x)
next_id = int(scores[0, -1].argmax())
ids.append(next_id)
```

`scores[0,-1]` 取第 0 条序列、最后一个输入位置的词表分数。把新 ID 接到末尾后再次前向，新位置便能预测再下一个 Token。这个过程每次只新增一个位置，但上下文逐步增长，因此一句话可以连续生成。

最直观的循环每次重新计算整个 `ids`。先理解这个版本，才能看出第 8.3 节缓存省去了什么。完整实现见 [generate.py](../inference/generate.py)，它没有调用 `model.generate()`：编码、前向、候选选择、追加、解码都在可读的程序里。

原生50M实现会屏蔽其独立PAD和BOS的生成分数。成熟模型应按自身生成配置处理特殊ID，不能机械照搬这两个屏蔽规则，尤其要核查PAD与EOS共用ID的情况。PAD 用于补齐批次，BOS 用于启动输入；一般回答中不希望它们重新出现。EOS 保持为合法候选，模型选到它时停止。除此之外，达到 `max_new_tokens` 或模型上下文上限也停止。限制新 Token 数可以防止短训模型永不结束或反复输出。

如果当前前缀有 `P` 个 Token、生成了 `G` 个 Token，那么已经使用的上下文为 `P+G`。原生50M配置虽然允许2048个位置，并不意味着其历史短窗口训练已充分学习该长度。成熟模型的上下文能力与本项目板端允许长度也要分开记录，部署从短上下文起步。容量限制与训练分布是两件需要分别记录的事。

固定 greedy 适合观察检查点变化，因为没有采样随机性。但它容易反复选择相同片段，也不会自动保证事实正确。错误答案在分数上最高，greedy 就会稳定选择错误答案。下一节只改变选择方法，观察同一权重能给出怎样不同的输出。


## 成熟模型的原生返回接口

以下是接口示意，前提是已用上游模型类加载匹配的 `model`、`tokenizer`，并准备好设备；本轮未运行该片段：

```python
messages = [{"role": "user", "content": "Linux是什么？"}]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, add_special_tokens=False, return_tensors="pt").to(device)
with torch.no_grad():
    scores = model(**inputs).logits
next_id = int(scores[0, -1].argmax())
```

这里编码器返回批次张量，前向返回对象中的 `.logits`；原生50M的 `tokenizer.encode(...).ids` 与默认直接返回张量是另一套接口。理解一轮计算后，循环继续追加ID、更新注意力掩码并按原生结束条件停止。不能把上面的单步片段当成已经完成的成熟模型生成器。

## 一次实际的结束边界错误

Qwen3.5本轮原生助手结束标记ID为248046，而语言配置中的文本结束ID为248044。早期评测只等待248044，模型即使选到正确的助手结束标记，也会继续生成模板换行或下一轮。于是正文只有“苹果”的回答可能被错误地当成“苹果加换行”，严格输出题也随之误判。

[成熟模型生成入口](../scripts/linux_assistant/evaluate.py)现通过 `generation_eos_ids` 同时使用原生助手与文本结束ID，发现停止ID后仍继续生成会直接报错。训练标签始终包含正确的助手结束标记，修复的是推理停止策略。旧完整轨迹保留，按首次助手结束截取的贪心Token前缀经过20个独立开发场景的GPU重放核对后重新评分；未重放题的修正计时留空。

这个例子中，特殊ID来自本轮固定Tokenizer，不能复制给50M或其他模型。严格格式只比较助手正文，不能把聊天模板的尾部当作模型回答；正文自己生成的多余字符仍然属于错误。
