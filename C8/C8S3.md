# 8.3 KV Cache、Prefill 与 Decode

模型、环境与目录见[教材基准](../docs/教材基准.md)；历史任务结果见[教学案例](../docs/cases/2B任务适配分析.md)，当前数据状态以[项目状态](../PROJECT_STATUS.md)为准。

假设提示编码成 20 个 Token。生成第一个新 Token 时计算这 20 个位置；生成第二个时若重新前向，就会计算 21 个位置，其中前 20 个已经做过。因果遮罩保证旧位置看不到新增的未来 Token，因此它们每一层的 Key 和 Value 不会因这次追加改变，可以保存下来复用。

首次处理完整提示叫 prefill。它在每层同时计算提示各位置，并保留 K/V。随后每次只输入刚生成的一个 Token，叫 decode；当前 Query 与“旧缓存加当前 K/V”计算注意力。缓存保存的是计算中间值，不是另一个模型的权重，也不保存旧位置的最终答案。

以现有原生50M缓存为具体算例，一个层缓存的K和V都是 `[B,n_kv,P,d]`。`B` 是批次条数，`n_kv` 是 KV 头数，`P` 是已处理长度，`d` 是每头维度。50M 使用 8 个 Query 头、2 个 KV 头，所以缓存保留 2 个头，而不是把 GQA 临时复制出的 8 个头全部存下。

总缓存字节数近似为：

$$
M_{KV}=2\times L\times B\times P\times n_{kv}\times d\times s_{bytes}
$$

开头的 2 分别计入 K 与 V，`L` 是层数，`s_bytes` 是每个浮点数的字节数。比如 11 层、单条序列、长度 32、2 个 KV 头、每头 64 维、BF16 两字节，得到 180,224 字节，约 176KiB。这里只计缓存张量，不计权重、当前激活和 GPU 工作区。

缓存版本要正确安排位置。若已经保存 20 个位置，新 Token 的 RoPE 位置是 20，不能又从 0 开始。遮罩也从正方形变成 `[当前长度,过去长度+当前长度]`：一条新 Query 可以看全部过去位置，但同一次追加多个 Token 时，较早的新位置仍不能看后面的新位置。

现有手写50M模型的可选接口如下，供原理对照，不是本轮新增的成熟模型接口：

```python
first = model(prompt_ids, use_cache=True)
next_step = model(
    next_ids, past_key_values=first.past_key_values, use_cache=True
)
logits = next_step.logits
```

`use_cache=False` 的默认调用仍直接返回 logits，保留第 3 章的行为。启用缓存时返回 `LubanOutput`，包含 logits 和逐层 K/V。实现见 [blocks.py](../model/blocks.py) 与 [luban_lm.py](../model/luban_lm.py)。缓存不写入 `state_dict`，因此不会改变严格权重映射。

验证不能只看程序速度提高。`python -m scripts.verify_gpu` 把同一串 ID 分为前缀和后缀，比较完整前向与带缓存后缀的 logits，还检查缓存头数、形状和因果性。训练开启梯度检查点时禁用缓存，避免在重算路径中混入不断增长的状态。

`eval.observe` 记录 prefill 单次耗时，并对同一提示分别开启与关闭缓存生成。总生成时间包含 prefill，不能冒充纯 decode 速度；模型提前输出 EOS 时，生成长度也会变短，应同时报告实际 Token 数。测得的数值见 [实跑报告](../docs/Windows实跑报告.md)。最后一节把这些步骤连接成可以输入问题的终端程序。

历史50M缓存开关对照使用FP32，避免将混合精度下不同矩阵形状的舍入差异混入输出比较；单独 prefill 与默认聊天使用 BF16。报告分别标明精度，不把两类计时当成同一个条件。


## 迁移到成熟模型

成熟模型使用上游实现的缓存对象和位置管理；具体容器随库版本变化，不能把 `LubanOutput` 或原生逐层元组强制传入。先用相同输入和精度比较完整前向与缓存后缀的logits，再检查多步生成和注意力掩码；当前这些验证待实现。公式可用于估算普通K/V张量，但板端峰值内存还包含权重、工作区与Runtime分配，不能据公式声称RK3576已测出某个占用。
