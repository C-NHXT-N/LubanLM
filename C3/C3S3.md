# 3.3 模型正确性验证

从教程目录执行；CPU例子沿用3.1节的 `$readerPython`，转换例子使用单独的 `$qwenPython` 环境。

上一节已经能调用完整模型，接下来要检查它是否按设计计算。先核对模块尺寸，再检查未来内容是否影响过去，最后看输出分数能否用于计算误差、反向传播和参数更新。模型即使能打印 logits，也可能在拆头、遮罩或目标错位上出错；这些检查帮助我们在正式训练前发现问题。

在 LubanLM 根目录的 PowerShell 中，用 C3.1 的 Miniconda 环境执行[验证程序](program/3.3/verify_model.py)：

```powershell
& $readerPython C3\program\3.3\verify_model.py
```

程序先读取 C2 的两份 JSON，核对参数量。手算数目来自各矩阵形状，模型数目来自 `model.parameters()` 中每个参数的元素数量；两者对上，才能排除漏层、漏 Norm 或输出头重复统计等错误。共享词表权重时，原公式为：

$$
P=VH+L\{2Hd(n_q+n_{kv})+3HI+2H+2d\}+H.
$$

这里 V 等于词表大小 `V_vocab`，H 是隐藏宽度，L 是层数，`n_q/n_kv` 是两类头数，d 是头宽度，I 是前馈中间宽度。花括号内依次统计 Attention、SwiGLU 和每层四个 Norm，末尾 H 是 Final Norm。共享 LM Head 不再加一份 VH。逐项来源已在 [C2.4](../C2/C2S4.md)计算，本节检查代码创建的参数是否一致。

0.5B 不必为了数参数而分配全部权重。程序在 PyTorch 的 `meta` 设备上创建模型：只登记各参数的形状，不保存实际数字，再对元素数量求和。按候选配置，应得到：

```text
LubanLM-50M:   49,558,400
LubanLM-0.5B: 488,964,864
```

若当前 PyTorch 无法使用 `meta`，脚本会打印原因并回退到参数公式。回退结果只能核对公式和配置，不能当成对真实模块形状的独立统计；看输出时应同时确认所用方法。

随后程序创建一份真正保存数值的微型模型：`V_vocab=64,H=32,L=2,n_q=4,n_kv=2,d=8,I=64`。它保留模块顺序与运算方式，只缩小尺寸，因此能低成本检查前向和梯度。这里与 C2 的六项词表算例用途不同：64 项配置专供自动验证，不是正式 Tokenizer 或训练规格。

先分别输入一条与两条长度为 5 的序列，检查外部形状：

|输入 ID|Embedding/Block 中间表示|输出 logits|
|---|---|---|
|`[1,5]`|`[1,5,32]`|`[1,5,64]`|
|`[2,5]`|`[2,5,32]`|`[2,5,64]`|

再单独检查一层 Attention 与 MLP 的输出均为 `[2,5,32]`，能与 H 维残差相加；gate/up 应为 `[2,5,64]`，对应中间宽度 I。这个配置的 I 与词表大小恰好都为 64，但两条轴含义不同：gate/up 的最后一维是中间特征，logits 的最后一维是 Token 分数，不能因为数字相同就混读。

形状正确还不足以证明信息流正确。程序使用 `[7,11,13,17]`，再将最后一个 ID 改成 23，保持前三个不变。因果模型的前 3 个位置不能读取第 4 个位置，所以这两次前向的前 3 组 logits 应在数值容差内一致。如果不一致，就回到注意力分数矩阵：行应为 Query 位置、列应为 Key 位置，未来列应被遮住，Softmax 应沿 Key 轴计算。这个比较直接检查未来是否泄漏，并不比较 LubanLM 与 Hugging Face 的全部数值是否相同。

接着把 logits 与正确的后续 Token 对齐。假设一条序列为 `[a,b,c,d]`，模型会为四个输入位置各给一组分数；位置 a 的分数用来预测 b，位置 b 预测 c，位置 c 预测 d。最后位置 d 没有后续答案，本例不使用它的分数：

```text
用于训练的预测位置：a  b  c
对应的正确目标：  b  c  d
```

交叉熵（cross entropy）根据正确 Token 的预测概率计算误差，正确目标得到的概率越高，误差越小。PyTorch 函数接收原始 logits，内部完成相应的归一化计算，不需要先手动做 Softmax。验证程序的核心代码为：

```python
# 来自验证程序的片段；logits、input_ids 和 vocab_size 已由模型准备。
loss = torch.nn.functional.cross_entropy(
    logits[:, :-1, :].reshape(-1, vocab_size),
    input_ids[:, 1:].reshape(-1),
)
loss.backward()
```

`logits[:, :-1, :]` 保留前 `T−1` 个位置，`input_ids[:, 1:]` 保留后 `T−1` 个目标。`reshape(-1,vocab_size)` 把 B 条序列的预测位置排成二维表，每行给出一个位置的全部词表分数，行数为 `B×(T−1)`；`-1` 让 PyTorch 根据总元素数推断行数。目标则排成同样顺序的一列 ID。

`loss.backward()` 执行反向传播，根据误差计算参数梯度。梯度表示参数变化对误差的影响，后续优化器据此更新权重。程序检查 Loss 不是 NaN（无法表示的数值）或无穷大，也检查所有可训练参数都获得有限梯度。随机权重下没有固定的正确 Loss，重要的是它能计算、能回传，而且没有数值异常。

最后检查参数更新是否能推动学习。脚本让另一个微型模型反复读取四条相同的短序列，用 AdamW 优化器更新 100 步，再比较这批样本的起始与结束 Loss。运行时会打印：

```text
重复样本短训 Loss: <运行时初始值> -> <运行时结束值>（正确性演示，不是正式评估）
```

检查条件是结束值小于起始值。这说明当前梯度和优化器能够让模型学习这批重复数据，但不说明它会处理未见过的文本，也不能替代正式验证集评估。若没有下降，先核对错误信息、目标对齐和数值环境，再决定是否增加步数；不能只把训练延长就忽略实现错误。

只想检查形状、因果性和梯度时，可以跳过短训；需要观察更多更新时，可以改变步数：

```powershell
& $readerPython C3\program\3.3\verify_model.py --skip-overfit
& $readerPython C3\program\3.3\verify_model.py --steps 150
```

正文中的参数量和形状来自配置推导，具体 Loss 与通过状态以每次运行输出为准；本机结果见[环境与验证记录](../环境与验证记录.md)。这些检查确认的是 PyTorch 内部计算。下一节还要把权重和 Tokenizer 整理成转换工具能读取的目录，再尝试生成部署文件。
