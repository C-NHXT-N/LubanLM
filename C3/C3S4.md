# 3.4 模型格式与 RKLLM 转换验证

从教程目录执行；CPU例子沿用3.1节的 `$readerPython`，转换例子使用单独的 `$qwenPython` 环境。

> 路线更新：本节是自训50M架构导出与兼容性的可选实验，旧结果按历史保留。50M训练阶段已结束；成熟模型的转换与板端预检另见 [9.1](../C9/C9S1.md) 和 [10.1](../C10/C10S1.md)，本节的自定义映射不用于成熟Qwen或LoRA合并。

上一节确认了 PyTorch 模型能按设计计算。本节保留早期在长训练前将随机初始化50M交给转换工具的实验，用于理解结构与文件格式的关系；它已不再是50M教学主线的必修关卡。本节先整理标准模型目录，再尝试在 PC 侧导出 `.rkllm`；开发板加载和推理留到部署章节。

这些阶段需要的文件不同：

|阶段|输入或产物|交给谁|
|---|---|---|
|PyTorch 模型|代码、配置和权重张量|PyTorch 执行前向与训练|
|标准模型目录|`config.json`、`model.safetensors`、Tokenizer 文件|模型加载器与转换器读取|
|Toolkit 转换|标准目录和目标平台、上下文等选项|PC 侧构建部署文件|
|板端运行|`*.rkllm` 和匹配的 Runtime|RK3576 加载并推理|

例如 `.pt` 或 `.safetensors` 可以保存权重，但转换器还需要知道每个参数属于哪一层、模型如何连接、ID 如何对应文本。把权重文件改成 `.rkllm` 扩展名并不会补上这些信息，也不会执行格式转换。

## 在 Windows 准备标准模型目录

本课程的[目录准备程序](program/3.4/prepare_rkllm_model.py)先按 C2 配置创建随机 LubanLM，再创建 Hugging Face 的 `Qwen3ForCausalLM`，将前者的权重严格载入后者。这里选择 Qwen3，是为了尝试 RKLLM 已列出的模型读取路径；权重仍来自我们随机初始化的模型。

“严格载入”表示逐一检查参数名称与形状：少了参数、多了参数或形状不同都会停止。它能确认权重组织对应，不证明两个实现的全部输出完全相同，也不保证后面的 Toolkit 构建成功。只修改配置里的架构名称，无法代替这些检查。

此节保留Toolkit1.3.0的历史映射研究，当前成熟模型主线为1.3.1。为避免改动3.1节CPU环境，目录准备使用独立Qwen环境，安装见[教材基准](../docs/教材基准.md)：

```powershell
$qwenPython = (Resolve-Path ..\.conda\qwen-py311\python.exe).Path
& $qwenPython -c "from transformers import Qwen3Config, Qwen3ForCausalLM; print('Qwen3 import OK')"
```

导入成功后，还需要 C1 最终确定并导出的 Fast Tokenizer。它的实际词表大小必须与 C2 配置相同，且包含 `<pad>`、`<bos>`、`<eos>`。当前候选是 32,000；若实际大小不同，应先更新配置，再复算 C2 参数量。`demo-320` 不能直接配上 32,000 行 Embedding，这一前提不能用随意补行掩盖。

在 LubanLM 根目录的 PowerShell 中执行下面命令。将 Tokenizer 路径换成实际目录，输出应选择尚不存在的新路径：

```powershell
& $qwenPython C3\program\3.4\prepare_rkllm_model.py `
  --config C2\program\2.4\config_50m.json `
  --tokenizer-dir artifacts\tokenizers\LubanTokenizer-32k `
  --output-dir artifacts\rkllm\LubanLM-50M-Qwen3
```

程序本身不会联网下载权重或依赖。它读取 Tokenizer 的实际大小和特殊 ID，写入模型配置，然后通过 `load_state_dict(..., strict=True)` 检查按模块名称保存的权重字典，最后保存模型和 Tokenizer。成功后目录应包含：

```text
LubanLM-50M-Qwen3/
  config.json
  model.safetensors
  tokenizer.json
  tokenizer_config.json
  ...Tokenizer 保存的其他配置文件
  lubanlm_conversion_manifest.json
```

清单记录来源配置、随机权重、参数量、特殊 ID 和依赖版本，RKLLM 转换状态仍是 `not_run`。看到“严格映射：通过”只表示完成了这一阶段，接下来要让真正的转换工具读取目录。

## 在 WSL/Linux 准备转换环境

RKLLM Toolkit 在 PC 侧解析模型、构建计算图并导出部署格式；RKLLM Runtime 是板端加载文件并执行推理的 C/C++ 接口。Rockchip [1.3.0 README](https://github.com/airockchip/rknn-llm/blob/release-v1.3.0/README.md)列出 RK3576 和 Qwen3 支持，本节据此选择这条转换路径。支持列表并不覆盖任意自定义尺寸与设置，50M 候选仍须实际尝试。

本节所用官方 wheel 是 `linux_x86_64` 安装包，不能装入刚才的 Windows 环境。进入 WSL Ubuntu 后，需要使用 Linux 版 Miniconda；Windows 的工作区Conda环境 与 Linux 环境各自保存对应系统的 Python 和依赖。

若 WSL 已有 Linux Miniconda，使用现有安装即可。若尚未安装，以下命令适用于 `uname -m` 输出 `x86_64` 的 WSL/Linux：从 [Miniconda 官方目录](https://repo.anaconda.com/miniconda/)下载 Linux 安装包到 D 盘映射路径，并在该路径安装。安装目录已存在时跳过安装，不覆盖已有环境：

```bash
uname -m
mkdir -p /mnt/d/conda-rkllm/installers
curl -fL https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh \
  -o /mnt/d/conda-rkllm/installers/Miniconda3-Linux-x86_64.sh
bash /mnt/d/conda-rkllm/installers/Miniconda3-Linux-x86_64.sh \
  -b -p /mnt/d/conda-rkllm/miniconda3
```

`/mnt/d/` 对应 Windows D 盘。下面假设 Linux Miniconda 安装在上述路径；已有安装则替换 conda 可执行文件的路径。我们按明确前缀创建 Python 3.10 环境，并把 Conda 包缓存也放在 D 盘：

```bash
export CONDA_PKGS_DIRS=/mnt/d/conda-rkllm/pkgs
/mnt/d/conda-rkllm/miniconda3/bin/conda create \
  --prefix /mnt/d/conda-rkllm/envs/luban-rkllm-130 \
  --override-channels --channel conda-forge python=3.10 pip -y
```

官方[安装包目录](https://github.com/airockchip/rknn-llm/tree/release-v1.3.0/rkllm-toolkit/packages)分别提供 Python 3.9、3.10、3.11、3.12 的包。文件名中的 `cp310` 对应 Python 3.10，`linux_x86_64` 对应系统与处理器架构，三者必须匹配。官方对 Python 3.12 另有 `BUILD_CUDA_EXT=0` 要求，本节选 3.10，避免混用另一版本的安装步骤。

接着在 WSL 克隆所选版本，并用 Linux 环境的解释器安装依赖与 wheel。仓库目录已经存在时，先确认版本，不重复克隆到同一目录：

```bash
mkdir -p /mnt/d/conda-rkllm/src
git clone --branch release-v1.3.0 --depth 1 \
  https://github.com/airockchip/rknn-llm.git \
  /mnt/d/conda-rkllm/src/rknn-llm-v1.3.0

/mnt/d/conda-rkllm/envs/luban-rkllm-130/bin/python -m pip install \
  --cache-dir /mnt/d/conda-rkllm/pip-cache \
  -r /mnt/d/conda-rkllm/src/rknn-llm-v1.3.0/rkllm-toolkit/packages/requirements.txt
/mnt/d/conda-rkllm/envs/luban-rkllm-130/bin/python -m pip install \
  --cache-dir /mnt/d/conda-rkllm/pip-cache \
  /mnt/d/conda-rkllm/src/rknn-llm-v1.3.0/rkllm-toolkit/packages/rkllm_toolkit-1.3.0-cp310-cp310-linux_x86_64.whl
/mnt/d/conda-rkllm/envs/luban-rkllm-130/bin/python -c \
  "from rkllm.api import RKLLM; print('RKLLM API import OK')"
```

D 盘挂载目录可避免文件落到默认系统盘，但 Linux 依赖涉及大量小文件，安装可能比 WSL 自己的文件系统慢。若调整存储位置，仍需保留独立环境和明确的下载缓存位置。安装完成后记录实际 Toolkit、Python 与依赖版本；`release-v1.3.0` 是所选发布引用，复现实验还应保留克隆出的提交号。换 Toolkit 版本时要重新核对依赖和 API，不能只根据“最新”二字替换文件。

## 导出并记录结果

Windows 上准备的标准目录可以从 WSL 的 `/mnt/d/` 访问。进入课程根目录，用 Linux 环境运行[转换程序](program/3.4/convert_rkllm.py)：

```bash
cd "/mnt/d/BaiduSyncdisk/知识库/LubanLM"
/mnt/d/conda-rkllm/envs/luban-rkllm-130/bin/python C3/program/3.4/convert_rkllm.py \
  --model-dir artifacts/rkllm/LubanLM-50M-Qwen3 \
  --output artifacts/rkllm/LubanLM-50M-RK3576.rkllm \
  --target-platform RK3576 \
  --num-npu-core 3 \
  --max-context 2048
```

脚本默认在 CPU 上加载、关闭量化，先确认工具能否接受结构。它沿用 [Rockchip 1.3.0 导出示例](https://github.com/airockchip/rknn-llm/blob/release-v1.3.0/examples/rkllm_api_demo/export/export_rkllm.py)的调用顺序：`load_huggingface` 读取目录，`build` 按目标平台构建，`export_rkllm` 写出文件。每一步都检查返回码；任一步非零就停止，因此要记录具体失败阶段。

如果以后要量化，再提供 `--quantize --calibration-data 文件.json`，用有代表性的文本校准。当前权重是随机数，不能拿它评价量化后的语言质量。量化类型、算法、上下文长度和 NPU 核数都属于工具构建选项，修改后需要重新记录，不能沿用上次结论。

成功时三个返回码应为 0，输出文件应存在且非空；程序还会写出 `.rkllm.manifest.json`，保存 Toolkit 版本、平台、量化设置、上下文长度和文件大小。清单中的 `board_runtime_test` 仍为 `not_run`，因为 PC 导出没有执行开发板程序。

下面的表用于真实转换后填写。默认参数量来自 32,000 词表的 50M 候选；若实际配置改变，应填写复算结果。本文列出的是操作流程，本次是否执行及环境状态见[环境与验证记录](../环境与验证记录.md)：

|记录项|应填写的内容|
|---|---|
|日期、主机、WSL 发行版|真实运行环境|
|Python、Toolkit、依赖版本|实际版本及官方仓库提交号|
|模型配置、参数量|候选为 49,558,400；修改后重算|
|Tokenizer 目录、实际词表、特殊 ID|实际产物的信息|
|Qwen3 严格权重映射|通过或完整错误|
|`load_huggingface`|返回码与日志|
|`build`|返回码、目标平台、核数、上下文与量化设置|
|`export_rkllm`|返回码、文件路径与大小|
|完整日志|可复查的保存路径|
|板端 Runtime 加载与推理|后续章节实测；未运行就记 `not_run`|

失败时沿阶段回查：Tokenizer 大小不符，回到 C1/C2；无法导入 Qwen3，检查当前解释器与 Transformers；严格映射失败，检查参数名称、形状和偏置；Toolkit 报不支持某层，检查实际运算与支持范围；平台选项报错，核对目标平台要求。每次只改一个设置，并保留原配置和完整错误，才能判断修改产生了什么影响。

生成非空 `.rkllm` 后，下一步是将它交给开发板上匹配的 Runtime、驱动和系统环境，实际加载并推理。只有完成那一步，才能记录板端验证结果；本节的随机权重转换也不承担语言能力或运行速度评估。

2026-10-02 的 Windows 后续流程使用 `--checkpoint` 导出实际训练的 50M Base/Chat，另验证 HF 与原生重新加载的 logits。未传这个参数时，本节脚本仍只准备随机模型。实际结果见 [Windows 实跑报告](../docs/Windows实跑报告.md)；这些检查不代替 WSL 的 RKLLM 转换。
