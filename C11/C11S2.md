# 11.2 首Token与生成速度

端到端首字计时从前端开始渲染模板、分词起，到第一个完整可见UTF-8文本输出止。C++首Token回调时间另存，两者不应混为一个指标。模型加载和预热不在这轮短输入首字计时内。

## 先算一条已有记录

继续第10.2节的[真实intro记录](../docs/cases/board-intro.json)：Qwen3.5-2B原模型，LubanCat-3/RK3576、W4A16、Runtime1.3.1，round=1，warmup=false。原始计时为：

| 字段 | 实测值 | 它从哪里计时 |
|---|---:|---|
| first_token_seconds | 0.848419秒 | 调用推理到第一次NORMAL或WAITING回调 |
| seconds | 8.49329秒 | rkllm_run调用到返回 |
| prefill_tokens / prefill_ms | 44 / 846.417毫秒 | Runtime报告的提示处理 |
| generate_tokens / generate_ms | 42 / 7642.17毫秒 | Runtime报告的生成阶段 |

把毫秒除以1000再相除，Runtime生成吞吐为 `42/(7642.17/1000)=5.4958 token/s`。若将同一数量除以整次调用时间，则为 `42/8.49329=4.9451 token/s`。后者包括提示等待，两个值回答的是不同问题。这条测量的首回调约848毫秒，也不能写成“用户848毫秒看到首字”：旧测试器在WAITING状态也可能记下首次回调，而且没有测前端分词与中文解码的耗时。

生成Token计数字段由Runtime定义；本条callback_token_ids有43项，末项是248046，正文前有42项。数值恰好对应本条记录，也不能据此假设所有Runtime计数都与可见Token一一相等。原始记录没有每个Token的时间戳，因此无法追溯下文的首末Token吞吐或端到端首字延迟。这两项应记未测，不能拿总时长减首回调来冒充最后一个Token时间。

可在普通Python中复算，不需要板卡：

```python
import json
from pathlib import Path

r = json.loads(Path("docs/cases/board-intro.json").read_text(encoding="utf8"))["record"]
print(r["generate_tokens"] / (r["generate_ms"] / 1000))
print(r["generate_tokens"] / r["seconds"])
```

从教程根目录运行，输入随书提供，几秒内结束，结果直接打印。若找不到文件，先核对当前目录；不要改用其他模型的汇总数字替换。两轮16题的原模型Runtime速度中位数约5.52 token/s，属于历史短测，不能据单条5.50宣称已达到新任务模型的20题验收目标。

## 统一吞吐口径

对回调中非结束Token计数为N，首末Token时间为t_first和t_last，本轮生成吞吐为：

```text
(N - 1) / (t_last - t_first)
```

例如生成21个非结束Token，首末回调相隔5秒，速度为(21−1)/5=4 token/s；这是口径示例，不是本轮成绩。

该口径不包含首Token等待，包含回调处理开销。Runtime自报prefill和generate的数量、时间另外保留，不能把不同计时口径拼成一个成绩。N不足2或时间间隔无效时不生成虚假的速度。

固定20条完整输入不超过128 Token，记录逐条Token数、停止原因、首字时间与生成速度。目标为首字P95不超过3秒、生成速度中位数至少4 token/s，且至少18条具有有效decode速度样本。所有20条都必须具有首字计时，不能删除慢样本或错误样本。

当前原模型历史短测与新任务模型分别记录；新模型没有实际通过前，不沿用原模型速度作为新成绩。更长输出、更长输入或不同温度条件需要另做实验。
